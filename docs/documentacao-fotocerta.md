> Documento de contexto para a base de conhecimento do projeto. Resume tudo que foi construído e as regras técnicas aprendidas. Última atualização: 20/08/2026.

## 1. Visão geral

- Negócio: **Foto Certa**, estúdio de fotografia (Vitória/ES). Identidade visual: coruja-suindara.
- Site: **fotocerta.com.br**, plataforma **Alboom Prosite**.
- Agendamento: **TidyCal** (booking type `fotocerta/natal-2026`), pagamentos do TidyCal via Stripe.
- **Dados operacionais não ficam neste repositório.** WhatsApp comercial, chave Pix (com recebedor e cidade) e Client ID Live do PayPal são digitados na ferramenta e guardados no `localStorage` do navegador — os campos nascem vazios, com exemplo no placeholder. Como o repositório é público, nenhum desses valores é versionado.
- Formato esperado de cada um: WhatsApp em DDI+DDD+número só dígitos; chave Pix no formato aceito pelo BC (e-mail, telefone, CPF/CNPJ ou aleatória); recebedor com até 25 caracteres e cidade com até 15, ambos sem acento no código Pix gerado.

## 3. Manual do Prosite (manhas do sanitizador — CRÍTICO para qualquer código novo)

1. **Remove `onclick`/eventos inline** → sempre `addEventListener`.
2. **Corrompe strings contendo** `<script`, `</script>`, `<style`, `<iframe` dentro de JS (na publicação) → blindar com concatenação: `'<scr'+'ipt>'`, `'</scr'+'ipt>'`, `'<sty'+'le>'`, `'</sty'+'le>'`, `'<ifr'+'ame'`.
2b. **Duas sequências tiram o parser HTML do estado normal de `<script>`, inclusive dentro de uma string JS** — e a blindagem por concatenação do item 2 só cobre as tags que o gerador escreve, não o texto digitado pelo operador que vai parar dentro do script gerado:
    - `</` — fecha o elemento no primeiro `</script` do texto bruto;
    - `<!--` — leva ao estado *script-data-escaped* e, se vier um `<script` depois, ao *double-escaped*; dali o `</script>` legítimo do próprio bloco **deixa de fechar o elemento**, e o que vem depois dele na página é engolido junto.

    Onde o valor é consumido como HTML, `escHtml` já basta (escapa o `<`, o que neutraliza as duas). Onde o valor precisa chegar cru ao runtime — porque vai para `textContent` ou vira chave de `localStorage` —, usar `escJs` (em `index.html`), que é `esc()` mais `replace(/<\//g,'<\\/')` e `replace(/<!--/g,'<\\!--')`: **essas duas sequências e nada mais** — a barra invertida o parser HTML vê, e o interpretador JS descarta.
    - **Vale para o próprio `index.html` da ferramenta, não só para o código gerado**: um comentário no fonte da ferramenta contendo `<!--` e, depois dele, um `<script` literal joga o parser no estado *double-escaped* e o `</script>` final deixa de fechar o bloco — a ferramenta inteira para de carregar. Ao comentar essas regras, escrever "sequência de fechamento de script" em vez da sequência literal.
    - **Cobertura (ago/2026)**: `escJs` passou a valer em **todo** ponto das cinco abas antigas onde texto de campo livre entra numa string JS do bloco gerado (Slideshow: link e legenda; Leads: código, nome da página, os 4 trechos da mensagem, emoji, âncora e os 7 textos do pop-up; Checkout: Client ID, chave Pix, nome, cidade, código do pedido, produtos, opcionais, cupons e todos os `TXT_*`). TidyCal não usa `escJs`: seus dois campos livres vão para **atributo HTML** (`data-path`, `src`) e já usavam `escAttr` — escapar para o destino errado produziria entidade literal visível. Bordas não usa: seu único campo livre (`padding`) vai para **CSS**.
3. **Remove tags semânticas HTML5** (`<section>`, `<header>`, `<nav>`) mantendo o conteúdo solto → usar só `<div>`.
4. **A página publicada carrega jQuery da Alboom que sobrescreve `$` global** → embrulhar todo script em IIFE `(function(){...})()`.
5. **Editor ≠ publicado**: sempre publicar para testar. Console do Safari (Cmd+Option+C) é a ferramenta de diagnóstico.
6. **Componentes HTML vivem em iframe do mesmo domínio** → scripts atravessam via `contentDocument`/`frameElement`.
7. **O CSS do tema esconde radios/checkboxes nativos** dentro de componentes → desenhar marcadores próprios (input invisível + span estilizado com `:checked + span`).
8. **O tema centraliza textos** dentro de componentes → forçar `text-align:left` no card e nos elementos.
9. **At-rules (`@keyframes`, `@media`) só funcionam em `<style>`** — na Tag Head do site (Configurações → Códigos personalizados → cabeçalho), na Tag Body ou dentro de um componente HTML. **Nunca no campo CSS Customizado do componente**, que aceita apenas propriedades soltas. Com o `@keyframes` no head, animações em componentes funcionam normalmente (ver aba "Bordas com efeito"). A exceção que permanece: animar **elementos de texto do editor** do Prosite (reconstruídos na publicação) — considerar inviável.
    - **Campo CSS Customizado do componente**: as propriedades soltas são aplicadas direto no elemento raiz daquele componente — **não precisa de ID Html, classe nem seletor**. Se algum componente exigir regra completa, inspecionar o elemento publicado, pegar a classe gerada pela Alboom e levar a regra (com seletor) para o head.
10. **Sem acentos/emojis em código colado** (precaução com o validador); textos visíveis com acento OK.
11. Tag Body aceita `<style>` + `<script>`.

## 4. Ferramenta de construtores (arquivo `index.html`, em construtores.fotocerta.com.br)

Ferramenta de geração de códigos com **7 abas**, estado persistido em localStorage (chave `fcConstrutores`, por navegador/domínio). Cada aba tem também uma **biblioteca de presets** — configurações salvas com nome, para aplicar depois (ago/2026, fase 2 da evolução). Acima das abas há a barra do **preset geral**, que agrupa a configuração das seis abas para uma página de uma campanha, em chave própria (`fcConstrutoresGerais`, ago/2026, fase 3). Tudo isso **sai e entra em arquivo `.json`**, pelo painel de detalhes do preset geral (ago/2026, fase 4). À direita das abas fica o **painel consolidado**, que junta num campo só tudo o que vai para a Tag Head e para a Tag Body da página selecionada e lista, sem juntar, as saídas que vão para componentes (ago/2026, fase 5).

### Isolamento por aba (ago/2026) — cada aba salva, restaura e parte sozinha

O arquivo continua único (a separação em vários arquivos foi avaliada e recusada: o ganho de desempenho é nulo — a ferramenta carrega em ~24 ms e a versão separada fica 5,8% **maior** comprimida — e as falhas graves eram de desenho, não de arrumação). O que mudou foi o desenho:

- **`salvarEstado` e `restaurarEstado` viraram um registro de abas.** Cada aba tem `xColeta()` e `xRestaura(st)`, declaradas dentro do bloco da própria aba, e a lista `ABAS` diz quais chaves de topo do JSON pertencem a quem (`imgs`+`s` → Slideshow, `t` → TidyCal, `l` → Leads, `u` → Checkout, `b` → Bordas, `cmsgs`+`c` → Contagem). Cada aba entra num `try/catch` próprio. Antes eram duas funções de 152 linhas com **um** `try/catch` para as seis: renomear um único campo de uma aba fazia a ferramenta parar de salvar e de restaurar as configurações das outras cinco, em silêncio (medido: código do pedido, espessura da borda e código da campanha todos vazios, e nada gravado a partir dali).
- **O pedaço da aba quebrada é preservado**, não apagado, **dos dois lados**. `restaurarEstado` guarda o fragmento lido antes de tentar restaurar. Se a **coleta** falha, `salvarEstado` regrava esse fragmento. Se a **restauração** falha, a aba entra em `fcSoLeitura` e **para de coletar do DOM até a página ser recarregada** — porque o DOM dela ficou com padrões, ou meio restaurado, e não representa mais o que o operador tinha. Sem essa segunda metade a garantia seria unilateral e falsa: bastava uma tecla digitada em qualquer aba para o salvamento coletar esse DOM e sobrescrever o que estava gravado. Medido com estado gravado malformado, sem injetar código: `cmsgs` como objeto derrubava **40 dos 66 campos** da Contagem quando o operador mexia na aba TidyCal, e `u.prods` como texto zerava **chave Pix, Client ID e código do pedido** sem ninguém abrir o Checkout. Com as duas metades, a única perda é a dos bytes que já estavam corrompidos no disco (4 e 14 campos, respectivamente) — o resto volta inteiro assim que o defeito for corrigido, e enquanto isso a barra avisa que aquela aba não está gravando.
- **A ordem de `ABAS` repete a ordem antiga das chaves** (TidyCal antes de Leads) por **conveniência, não por necessidade**: a compatibilidade não depende dela — a restauração lê por chave, e uma cópia com a ordem visual foi testada e restaurou os mesmos campos. O que a ordem antiga compra é diff limpo quando uma regressão compara o JSON como texto. Reordenar é seguro; só custa ruído nesse tipo de comparação.
- **A partida também é por aba**, via `prep(nome, abaId, fn)`. Antes, uma exceção em `bToggles()` (Bordas) deixava `cToggles()`, `cMsgRender()` e `cPvBotoes()` (Contagem) sem rodar, e a aba Contagem nascia meio configurada por causa da aba ao lado. A barra de abas é o primeiro `prep` e vem sozinha: é o único passo que precisa sobreviver a tudo, senão a ferramenta inteira parece morta.
- **Compartilhadas no topo**: `escHtml`, `escAttr`, `escJs`, `corMockPP` e `mockPP` subiram para a seção de utilidades. Estavam declaradas dentro do bloco de uma aba e só funcionavam por hoisting (a TidyCal chamava `mockPP` 1.319 linhas antes de ela ser declarada, dentro de outra aba). Cuidado ao mover esse bloco de novo: o comentário e a expressão regular de `escJs` trazem `<!--` literal, e o parser HTML entra em estado escapado dali até o primeiro `-->` do arquivo — inofensivo enquanto nenhuma linha trouxer `<script` literal (a regra do Prosite já obriga a concatenação), mas o trecho afetado anda junto com o bloco.

**Falha isolada não pode virar falha muda.** Quando uma aba falha ao salvar, restaurar ou preparar, três avisos saem ao mesmo tempo: uma **barra vermelha fixa no topo** nomeando a aba e a fase (visível em qualquer aba — o operador pode nunca abrir a defeituosa), a marca **`(!)`** no botão da aba, e um `console.error` com a exceção inteira. Regras que sustentam esse contrato:

- **A barra diz *o quê*, a marca diz *onde*** — então passo que toca duas abas marca as duas (`fcMarcaAba` aceita `'leads uni'`); passo sem aba nenhuma não existe.
- **Cada combinação rótulo+fase avisa uma vez só**, porque `salvarEstado` roda a cada tecla e a barra viraria uma lista infinita da mesma linha. Como cada aba aparece **duas vezes** na fila de partida (ligar botões; desenhar com o estado restaurado), a segunda passagem declara uma `fase` própria — sem isso a falha dela ficaria escondida pela da primeira.
- **A barra compensa a própria altura** (`body.style.paddingTop`), senão cresceria a cada falha nova até cobrir os botões das abas — inclusive a marca `(!)` para onde ela aponta.
- **Falha ao restaurar diz que a aba parou de gravar**, não só que falhou. **Falha do próprio armazenamento** (indisponível, corrompido) usa a mesma barra, com texto que diz explicitamente que nada está sendo salvo.

### Biblioteca de presets por aba (ago/2026, fase 2 da evolução) — um preset é a fotografia do `coleta()`

Cada uma das **seis** abas tem a sua biblioteca: salvar a configuração da tela com um nome, aplicar um preset salvo, remover. A aba Bordas tinha isso desde a fase 5 anterior, com mecânica própria; a mecânica agora é **uma só, compartilhada**, e a das Bordas foi removida — duas implementações do mesmo recurso é o defeito que este projeto mais pagou para aprender.

**A costura é o registro `ABAS`.** Um preset guarda o que o `coleta()` daquela aba devolve, e aplicar chama o `restaura()` dela — o mesmo caminho do estado gravado. Não existe um segundo caminho de leitura ou de escrita de campos, e é isso que garante que "Aplicar" devolva a aba **inteira**: campo que entra no estado entra no preset pela mesma linha. Cada entrada de `ABAS` ganhou:

| Campo | Para que serve |
|---|---|
| `pref` | prefixo dos campos (`s-`, `l-`, …). É também a chave do fragmento (`s`, `l`, …) e onde a biblioteca fica gravada: `<pref>.presets` |
| `fora` | campos do fragmento que **não** entram num preset porque descrevem *outro* componente (hoje só `b.consol`, a consolidação do código 1). Ao aplicar, conservam o que está na tela |
| `operacionais` | `[chave, como aparece na interface]` dos campos de contato/pagamento. Fonte única: alimenta o aviso na aba, o "sem dados" da exportação (fase 4) e a comparação entre páginas da mesma campanha (fase 3) |
| `resumo` | a linha curta que descreve o preset na lista |
| `redesenhar` | o que refazer depois de aplicar — é o mesmo passo que a partida já executa "com o estado restaurado" |
| `antesDeSalvar` | recusa antes de congelar a configuração (prende os números à vista; nas Bordas, também recusa configuração que não gera código) |
| `presetOk` / `aposPresets` | conferência extra de formato e passo próprio da aba depois da lista (nas Bordas, repovoar a caixa de consolidação) |

**Onde e como fica gravado.** Dentro do fragmento da própria aba (`b.presets` já era assim antes, então a Bordas não mudou de lugar). Não há chave de topo nova, e por isso o isolamento por aba vale também para a biblioteca. Cada item:

```
{nome: '...', carimbo: <ms>, valores: {<fragmento da aba, sem a biblioteca e sem os campos 'fora'>}}
```

- **`carimbo` existe para a fase 3.** O preset geral vai guardar uma cópia dos valores mais uma marca de origem `{preset, carimbo}`; sem carimbo não haveria como avisar *"veio de 'X', que mudou depois"*. É a data de modificação em milissegundos. Regravar o mesmo preset com os **mesmos** valores **não** avança o carimbo (comparação por `fcValoresIguais`) — se avançasse, todo preset geral copiado dele se diria desatualizado sem nada ter mudado, e aviso falso gasta a confiança dos verdadeiros.
- **`fcCanon` / `fcValoresIguais`** são a forma de comparar dois conjuntos de valores da mesma aba: serialização canônica com as chaves ordenadas, então a mesma configuração dá a mesma string mesmo quando um lado veio do disco em outra ordem. É a peça que a fase 3 consome.
- **Compatibilidade.** Preset da Bordas no formato antigo (`{nome, cfg}`) é traduzido **na leitura** (`fcPresetConverter`) para `{nome, carimbo: 0, valores: {b: cfg}}` — carimbo 0 significa "data desconhecida" e é **estável** (usar a data de hoje faria o preset parecer modificado a cada abertura). A tradução é de mão única: uma versão anterior da ferramenta não lê o formato novo. Provado: com a biblioteca gravada no formato antigo e a consolidação apontando para um preset dela, o código 1 saiu **byte a byte idêntico** ao da versão anterior.
- **Leitura defensiva**, no mesmo critério que a Bordas já usava: item a item, e o que fica de fora é **anunciado na própria aba** ("2 itens da biblioteca estavam ilegíveis e ficaram de fora"), nunca some calado.

**Dados operacionais entram no preset — decisão consciente.** WhatsApp, chave Pix, Client ID, recebedor e cidade fazem parte da fotografia da aba; tirá-los faria "Aplicar" devolver a aba pela metade, em silêncio. O preset não sai do navegador: vive no mesmo `localStorage` onde esses campos já vivem, e as abas Leads e Checkout **dizem isso na tela**, nomeando os campos. O `resumo` da lista, ao contrário, **nunca** mostra esses valores — a lista fica à vista e sai numa captura de tela. Para a fase 4, a lista `operacionais` é o que a exportação "sem dados" vai limpar.

**Travas.** Aplicar passa pelo `restaura()` (onde `corValida` já atua) e depois pelo `redesenhar()`, que roda `fcAjustarTodos` — então preset com número fora da faixa **se corrige à vista** no campo, e tela e código gerado continuam mostrando o mesmo número. Medido com preset adulterado à mão: `mob` 99 → 320, `tam` 999 → 32, `vel` 0 → 2, com o `@media` do código saindo em 320px.

**Aba em só-leitura não opera presets.** A aba que falhou ao restaurar parou de coletar do DOM até a página ser recarregada; ali salvar leria campos que não representam nada, aplicar escreveria numa tela que não está sendo gravada e remover não seria persistido. Os três recusam com a mesma explicação, em vez de parecerem funcionar — e as outras cinco abas continuam salvando presets normalmente.

**Aparência.** Os dois fieldsets (salvar à esquerda, lista à direita) são montados por `fcPresetsMontar` a partir do registro — uma implementação de marcação e de texto para as seis abas, em vez de seis cópias que divergem na redação. A classe da lista virou `.fc-presets` (era `.b-presets`).

**Esquema de ID: `fcp-<pref>-<papel>`, e a varredura de IDs repetidos virou parte da verificação.** A primeira versão de `fcPresetsMontar` gerava `<pref>-pnome`. No Checkout isso deu `u-pnome` — **ID que a aba já usava** no campo *Nome do produto*. Dois elementos com o mesmo ID não produzem erro nenhum: `getElementById` devolve o primeiro do documento, que era o do produto. O estrago, medido pelo caminho real (digitando no campo e clicando no botão):

- o operador digitava o nome do preset na caixa da seção de presets e recebia *"De um nome ao preset antes de salvar"* — **a única das seis abas onde a biblioteca não podia ser criada pela interface**;
- com o formulário de produto preenchido, o preset nascia com o nome **do produto**, o nome digitado era ignorado e o campo do produto era **apagado**, deixando preço sem nome, **sem um único aviso**.

A correção não é trocar um nome, é escolher um espaço de nomes que não possa colidir de novo: tudo o que a biblioteca gera vive em **`fcp-`** (`fcp-<pref>-box`, `-nome`, `-salvar`, `-lista`). Campo de aba, por convenção deste arquivo, começa pelo prefixo de **uma letra** (`s-`, `t-`, `l-`, `u-`, `b-`, `c-`); nenhum pode se chamar `fcp-…` sem quebrar a própria convenção, então a coincidência de prefixo com nome de campo não volta. De quebra, `fcp-…` não casa com os listeners de "mudou alguma coisa nesta aba", e a exceção que existia só para isso (`fcCampoDePreset`) saiu — ela também estava desligando a prévia do Checkout ao digitar o *Nome do produto*.

**Verificação obrigatória a partir daqui:** com a página servida por `localhost`, rodar a varredura de IDs repetidos no documento inteiro e exigir **zero**:

```js
var t=document.querySelectorAll('[id]'),v={},d=[];
for(var i=0;i<t.length;i++){ if(v[t[i].id]) d.push(t[i].id); else v[t[i].id]=1; }
d;   // tem de sair []
```

A varredura não é cerimônia: rodada no commit anterior ela aponta exatamente `u-pnome`, e no atual sai vazia com os mesmos 364 IDs. E o teste tem de ser feito **digitando no campo que está dentro da seção de presets** — roteiro automatizado que escreve por `getElementById` acerta o mesmo elemento errado que o código lia e **passa** com o defeito de pé.

**Texto livre vazio é escolha, não campo ausente.** `uRestaura` lia `t7`..`t10` (os quatro rótulos livres do Checkout: *Escolha seu ensaio*, *Sinal agora*, *Restante na entrega*, *Resumo para conferencia*) com guarda de verdade — `if(U.t7)` —, enquanto `uColeta` os grava sempre. Como nenhum é número, o clamp não os alcançava: esvaziar os quatro e aplicar um preset **devolvia a aba pela metade**, em silêncio, e o operador publicava um checkout com os rótulos da campanha errada. A guarda passou a ser `!=null`: estado gravado por versão anterior (que não tem a chave) continua deixando o padrão do HTML de pé, e o vazio passa a ser honrado. **Honrar** foi a escolha, e não corrigir para o padrão à vista, porque o gerador **já aceita o vazio** — `uGerar` lê o campo direto e emite `TXT_PRODUTOS=''` sem quebrar nada; tela e código gerado já concordavam, era só a restauração que discordava dos dois. A regra geral que fica: **campo numérico e cor se corrigem à vista** (não existe vazio que faça sentido neles); **texto livre honra o vazio**. Varridas as outras cinco abas, nenhuma outra guarda de verdade sobre texto livre foi encontrada, e o ida-e-volta com todos os campos de texto vazios volta idêntico nas seis.

**Correção à vista das cores livres vale nas quatro abas que as têm (ago/2026, fase 2.5).** `CORES_LIVRES` cobria só Leads e Checkout; Bordas e Contagem ficaram de fora porque `corSegura` já protegia o **código gerado**. Só que ela não protege o **campo**: medido em `main`, esvaziar `b-c1-t` e clicar em *Gerar código* deixava o campo **vazio na tela** e mandava `#9C5638` para o CSS — tela e código discordando em silêncio, a classe de defeito que este projeto mais paga para aprender. As sete cores das Bordas (`b-f1`, `b-f2`, `b-c1`..`b-c4`, `b-pvcor`) e as dez da Contagem (`c-cfundo`, `c-ctexto`, `c-cdestaque`, `c-cborda`, `c-ctafundo`, `c-ctatexto`, `c-cprog`, `c-corujacorpo`, `c-corujadet`, `c-curg`) entraram na mesma lista, e com isso ganham de uma vez os três caminhos que Leads e Checkout já tinham: `change`/`blur` no campo, correção na carga do estado gravado e correção depois de aplicar um preset. Duas peças nasceram para não multiplicar cópia: `fcCoresAjustar(pref)` (o laço que estava copiado em `lPresetDepois` e `uPresetDepois`) e `fcCorRedesenhar(idBase)`, mapa por prefixo em vez de cadeia de `if` com ramo `senão` — o ramo `senão` era o do Checkout, e a aba esquecida na próxima vez cairia nele redesenhando a prévia errada, sem erro nenhum no console. **Nunca em `input`**: corrigir a cada tecla impediria digitar `#075E54`, porque `#0` viraria o padrão antes do resto chegar.

### Preset geral (ago/2026, fase 3 da evolução) — uma página de uma campanha, respondida uma vez só

Um **preset geral** é a configuração das **seis abas** para **uma página de uma campanha**. Ele responde "para qual página vai este código?" uma vez, em vez de seis (uma por aba): seis chances de inconsistência viram zero. Selecionado numa barra acima das abas.

**Dois campos, nome derivado.** `campanha` é texto livre com sugestão das campanhas já existentes (um `<datalist>`, para evitar "Natal 2026" e "Natal26" convivendo por engano) e `pagina` é escolha fechada entre *hospedeira* e *embutida*. O nome exibido — `Natal 2026 · Hospedeira` — **nunca é digitado**: é derivado dos dois. Nome livre impediria a ferramenta de saber que duas páginas pertencem à mesma campanha, que é o que sustenta o seletor agrupado (`<optgroup>` por campanha) e o aviso de divergência.

**O rascunho continua sendo a tela, e a chave antiga não é tocada.** Os presets gerais moram numa chave própria, `fcConstrutoresGerais`; `fcConstrutores` — o estado das seis abas — continua exatamente como era. Duas consequências medidas: quem nunca criar um preset geral tem a ferramenta de antes (sem preset selecionado, o estado "Rascunho", nada na tela muda e nada é gravado na chave nova), e um defeito na camada nova **não pode corromper a configuração das abas**. Provado com a chave nova contendo JSON inválido: a barra vermelha diz o que houve, o preset geral cai para Rascunho e as seis abas, com a biblioteca de presets de cada uma, voltam inteiras.

> **A ressalva que a frase acima esconde, dita em voz alta: adotar um preset geral sobrescreve `fcConstrutores` sim.** Não pode ser diferente — adotar reescreve a tela, e a tela **é** o rascunho, então o `salvarEstado` seguinte grava a chave antiga com os valores do preset. "A chave antiga não é tocada" é verdade para a contabilidade da camada nova (ela guarda o que é dela na chave dela) e para quem nunca usa o recurso; **não** é verdade para `fcgAdotar`. O que separa isso de perda de trabalho é a pergunta de três saídas, que sempre precede a adoção e **nomeia** o que se perde. Medido nesta rodada: a ida-e-volta completa das seis abas (adotar o mesmo preset duas vezes, e descartar alterações) devolve `fcConstrutores` **byte a byte idêntica** — a sobrescrita é a configuração pedida, não uma deformação dela.

**Não há segundo caminho de leitura nem de escrita.** Os valores de uma aba saem de `fcPresetCapturar(a)` — o mesmo `coleta()` que alimenta o estado gravado e a biblioteca de presets — e voltam pelo `restaura()` da própria aba, seguido do `redesenhar()`. Aba em `fcSoLeitura` é o único desvio, e ele **também** é o que `salvarEstado` já fazia: os valores vêm do último fragmento bom (`fcFrag`), sem `presets` e sem os campos `fora`. Sem isso, a alternativa seria recusar salvar o preset geral inteiro por causa de uma aba quebrada, e o operador perderia o trabalho das outras cinco. Ao **aplicar**, a aba em só-leitura é pulada e nomeada num aviso.

**Cada aba está `ativa` ou `fora` da página, e o padrão ao criar é FORA.** A barra de abas mostra o estado — aba fora fica esmaecida e ganha um selo, **continuando clicável** (é preciso poder abri-la para ligá-la) —, e no topo de cada aba há o interruptor. Desligar **preserva os valores**: eles continuam na tela e no preset, e voltam ao religar. O padrão "todas fora" é deliberado: aba esquecida *fora* falha de forma **visível** (falta um bloco na página, o operador percebe); aba esquecida *dentro* falha de forma **invisível** (um bloco a mais numa página publicada). É a mesma regra que decidiu o clamp à vista dos campos numéricos.

> **O selo "fora" é curto de propósito.** A frase inteira, "fora desta página", vai no `title` e no `aria-label` do botão, e aparece por extenso no interruptor dentro da aba. Escrita nos seis botões — que é o estado inicial de todo preset geral novo — ela daria uma barra de abas de três linhas. `.abas` ganhou `flex-wrap:wrap` no mesmo movimento, o que de quebra fecha um estouro de 11 px que já existia em janela de 700 px.

**Cópia com marca de origem, nunca ponteiro (`origem: {preset, carimbo}`).** Aplicar um preset de aba com um preset geral selecionado anota de onde a cópia veio. Ponteiro não serve: editar um preset de aba mudaria em silêncio todas as campanhas que o usam, e apagá-lo quebraria os presets gerais. Os quatro estados saem de duas perguntas, e as duas usam só o que a fase 2 deixou pronto:

| Pergunta | Resposta | O que a aba diz |
|---|---|---|
| o preset de aba com aquele nome ainda existe? | não | *"A origem não existe mais."* — **nada quebra**: os valores são cópia e continuam inteiros |
| o `carimbo` dele é o mesmo de quando a cópia foi feita? | não | *"Veio de 'X', que mudou depois"* — com **ver diferença / atualizar / desvincular** |
| (carimbo igual) os valores conferem? | não | *"Modificado a partir de 'X'"* |
| | sim | *"veio do preset 'X', e continua igual a ele"* |

Se o carimbo é o mesmo, então os valores do preset **são** os valores copiados — a fase 2 garante que o carimbo só avança quando os valores mudam —, e é isso que permite distinguir "a origem mudou" de "a cópia foi editada" sem guardar uma segunda cópia dos valores. **Nunca atualiza sozinho:** "Atualizar com o preset" confirma dizendo quantos e quais campos mudam de valor. "Ver diferença" lista os nomes **internos** dos campos e diz que são internos — inventar rótulo bonito para os ~60 campos seria uma segunda tabela de nomes, que divergiria da primeira no dia em que um campo fosse renomeado.

**Aviso de divergência entre as duas páginas da campanha.** Quando a **mesma** aba está ativa nas **duas** páginas e um campo `operacionais` (WhatsApp, chave Pix, Client ID, recebedor, cidade) tem valor diferente, a aba mostra aviso âmbar **nomeando o campo**. Não bloqueia — pode ser intencional. Só dispara com a aba ativa dos dois lados: sem isso não há o que comparar. A lista `operacionais` de `ABAS` é a fonte única do nome que aparece na tela, a mesma que a fase 4 vai usar para limpar o arquivo "sem dados" — e como cada rótulo dela já traz o artigo ("o número do WhatsApp", "a chave Pix"), a frase diz *"tem outro valor **para** …"*: prefixar `em ` produzia "em o número do WhatsApp".

**Nenhum caminho destrutivo é silencioso.** Trocar de preset com alterações não salvas **bloqueia** e oferece três saídas — salvar / descartar / cancelar —, listando exatamente o que se perde ("a aba 'Slideshow' foi ligada nesta página", "os campos da aba 'Checkout' mudaram"). Sair do Rascunho para um preset avisa que a tela será substituída e oferece guardá-la antes. Apagar um preset geral confirma dizendo quais abas estavam ligadas nele e que **a tela não é apagada** — continua lá, como rascunho. Renomear (mudar campanha ou página e salvar) confirma com o nome velho e o novo, e renomear **para uma combinação que já existe é recusado**, não fundido: fundir apagaria o outro preset.

> **Por que renomear não conta como "alterado".** Flipar o rádio para *Embutida* é o gesto natural de quem vai criar a segunda página. Se isso contasse como alteração, a pergunta de troca ofereceria "salvar antes" — e salvar **renomearia** a página Hospedeira para Embutida, o oposto do que o operador quis. Por isso os campos de identidade ficam fora de `fcgMotivos`, e renomear é um passo declarado, com confirmação própria.

**Um botão que promete um nome salva naquele nome.** A decisão acima tem um flanco, e a composição que o abre é justamente o gesto documentado: em *Natal 2026 · Hospedeira*, flipar o rádio para **Embutida**, ter uma edição não salva e clicar **Salvar como preset geral**. O primeiro botão da pergunta diz *"Salvar em 'Natal 2026 · Hospedeira' antes"* — e a primeira versão o cumpria lendo os campos do painel, que já diziam Embutida: renomeava a Hospedeira e em seguida recusava criar, por colidir com o preset que acabara de renomear. A campanha terminava com **uma página só**, e a confirmação de renomear ainda aconselhava usar a ação em andamento. Salvar passou a ter dois caminhos com nomes diferentes: `fcgSalvarNoAtivo` (o botão **Salvar** da barra) lê os campos e **pode renomear**, com confirmação; `fcgSalvarComoEsta` (os botões "salvar antes"/"salvar e trocar" das perguntas) grava no preset ativo **com o nome dele**, sem ler campo nenhum, sem reescrever os campos e sem ter como falhar. As duas usam o mesmo miolo, `fcgGravarNoPreset`. Medido depois: a composição inteira termina com **as duas páginas**, a Hospedeira com a edição salva e a Embutida criada.

**"Outros códigos meus" não viaja entre páginas.** Os dois campos são da página, como as abas — mas as abas têm interruptor e **nascem fora**, e estes dois não têm interruptor nenhum. A proteção equivalente é **não copiar**: preset geral criado a partir de outro preset geral nasce com os dois vazios (e o aviso de criação diz isso), e sair para o Rascunho também os esvazia, porque o Rascunho não é uma página. Nascendo do Rascunho eles vão junto — ali foram digitados para esta página, e não há outra de onde tenham vindo. Sem isso, medido: com o Tag Head da Hospedeira do Natal na tela, criar `Pascoa 2027 · Hospedeira` fazia a campanha nova **nascer carregando o Tag Head do Natal**, invisível com o painel recolhido. Quando a fase 5 colar `codigos.head` na página, seria exatamente o "bloco a mais numa página publicada" que o padrão *fora* existe para impedir.

**Regravar o preset de origem recarimba a marca.** O gesto de rotina é aplicar o preset X, ajustar um campo e regravar X para capturar o ajuste. `fcPresetSalvar` avançava o carimbo e deixava a marca de origem para trás, então a aba passava a exibir o aviso âmbar *"Veio de 'X', que mudou depois"* com o painel logo abaixo dizendo **"Campos diferentes (0): nenhum"** — aviso falso num gesto corriqueiro, que é o que a regra do carimbo da fase 2 existe para evitar. `fcgOrigemRecarimbar` acompanha o carimbo novo, e só quando a origem **já aponta para aquele preset** (comparação de nome sem caixa e sem espaço, a mesma de `fcPresetIndice`): apontar a origem para outro preset seria decidir pelo operador de onde a configuração dele veio. É seguro porque o que foi gravado é o mesmo `fcPresetCapturar` que a tela devolve — o estado que fica é *igual* por ser verdade. Medido: a página cuja cópia é **realmente** anterior continua avisando "mudou depois", agora com campos diferentes de verdade na lista.

**Par (campanha, página) repetido no armazenamento é renomeado, não descartado.** Dois presets gerais da mesma campanha e da mesma página eram ambos lidos, mas só o primeiro respondia: o segundo não aparecia em lista nenhuma, não era contado e não gerava aviso — invisível e indelével. Pela interface ele é inalcançável (criar e renomear recusam colisão), mas o R4 da fase 4 promete "importar como cópia" em colisão de nome, e para preset geral isso produz exatamente esse par. Na leitura, o repetido ganha um número no fim do nome da campanha (`Natal 2026 (2)`), aparece na lista, pode ser selecionado e apagado, e o renome é dito na barra vermelha uma vez. Entre descartar e mostrar, mostra.

> **A caixa de seleção nascia vazia.** `fcgRenderSel` só remonta quando a assinatura da lista muda, e a assinatura de "nenhum preset geral" é a string vazia — o mesmo valor com que a variável de controle era inicializada, então a **primeira** montagem era pulada e a caixa ficava sem opção alguma, nem a do Rascunho. Todo operador de primeira viagem via o controle principal da barra como uma caixa cinza vazia. A variável passou a nascer `null`, que nenhuma assinatura pode igualar.

**O selo é adiado; a decisão nunca é.** `salvo`/`alterado` é recalculado com debounce de 250 ms e **timer único**, porque comparar as seis abas custa seis `coleta()` clonados (com 46 fotos na lista, isso pesa). Mas **toda decisão que pode destruir trabalho recalcula na hora**: `fcgTrocarPara` chama `fcgMotivos()` sincronamente e nunca lê o selo.

**Quem acorda a barra é o `salvarEstado`, não os eventos de campo.** Ligar o redesenho aos eventos `input`/`change` de `document` parecia bastar e **não bastava**: adicionar uma foto, reordenar a lista, remover um produto, salvar ou remover um preset de aba mudam o estado por um **clique em botão**, e clique não dispara nem `input` nem `change`. Medido: removendo da biblioteca o preset de onde a aba tinha vindo, o aviso continuava dizendo *"veio de 'X', e continua igual a ele"* sobre um preset que já não existia. `salvarEstado` é o ponto por onde toda mudança de valor passa; a chamada entra ali, dentro de um `try` próprio, porque gravar é sagrado e um defeito no desenho da barra não pode impedir o salvamento que acabou de acontecer.

**Aparência: `fcg-` é o espaço de nomes, e só a linha gruda.** Tudo o que a fase 3 desenha vive em `fcg-…`, pelo mesmo motivo de `fcp-` na fase 2 — campo de aba começa por prefixo de **uma letra**, então a colisão que custou o `u-pnome` não pode voltar, e os listeners de "mudou alguma coisa nesta aba" (todos guardados por expressão regular de prefixo) não alcançam estes campos. A varredura de IDs repetidos sai `[]` com 401 IDs (369 antes). A barra usa `position:sticky`, e não `fixed`, porque a barra vermelha de falhas já é `fixed` no topo e compensa a própria altura empurrando o `body` — duas fixas se cobririam, e a de falha tem de vencer (z-index 99999 contra 50). Gruda **só a linha** (`.fcg-fixa`, 55 px), nunca o painel de detalhes: com o painel aberto a barra inteira tem 607 px e grudar isso comeria mais de meia janela. E `.fcg-fixa` é **filha direta do `<body>`**: `sticky` gruda dentro do bloco que a contém, e uma caixa de 605 px levaria a linha embora junto — medido, com o painel aberto e a página em 1200 px a linha ficava em `top:-547`, fora da tela, sem grudar em nada.

**"Outros códigos meus" (Tag Head e Tag Body) já é guardado, e ainda não é consumido.** Dois campos de texto por preset geral, para o código que o operador cola à mão e não sai de aba nenhuma. Como é por página, troca junto com a campanha. Quem vai juntá-los aos blocos gerados é o painel consolidado da fase 5; o texto de ajuda ao lado dos campos diz exatamente isso, para o campo não parecer que faz algo que ainda não faz.

**Preset geral é organização de ENTRADA.** Ele não pode mudar o que sai: as 9 saídas dos seis geradores foram comparadas byte a byte com as da `main` para a mesma configuração, em três cenários — Rascunho, preset geral com as seis abas ligadas e códigos manuais preenchidos, e preset geral com uma aba fora —, e nos três saíram idênticas (27 de 27). O `fcConstrutores` de cada cenário, semeado na `main`, volta idêntico depois de a `main` gerar por cima dele: a camada nova não deforma o que a antiga guarda — o que ela faz com a chave antiga é **reescrevê-la com o preset adotado**, a pedido, como está dito acima.

### Backup em arquivo (ago/2026, fase 4 da evolução) — o único jeito de a configuração sair do navegador

Dois botões de exportar e um de importar, no painel **Detalhes** da barra do preset geral. Tudo o que a ferramenta guarda vive no `localStorage` de **um** navegador: some ao limpar os dados do site e não acompanha outro computador. O arquivo é a saída.

| Botão | O que leva | Nome do arquivo |
|---|---|---|
| **Exportar tudo** | todos os presets gerais, as seis bibliotecas de presets de aba e o rascunho (a tela) | `construtores-fotocerta-AAAA-MM-DD-{com\|sem}-dados.json` |
| **Exportar este preset geral** | uma campanha-página, para repassar | `preset-<campanha>-<pagina>-{com\|sem}-dados.json` |

**O nome do arquivo é a salvaguarda, e por isso a escolha é na hora de exportar.** A pergunta tem duas saídas — *com os dados* e *sem os dados* — e **mostra os dois nomes escritos** antes de o operador escolher. Sem dados significa exatamente os campos de `operacionais` do registro `ABAS` (WhatsApp, chave Pix, Client ID, recebedor, cidade): a **mesma** lista que alimenta o aviso das abas Leads e Checkout e a comparação entre as duas páginas da campanha. Uma segunda lista aqui divergiria da primeira no dia em que um campo fosse acrescentado, e o arquivo sairia com dado dentro e o nome dizendo que não tinha. A pergunta também diz o que o "sem dados" **não** tira: as caixas "Outros códigos meus" viajam como estão nos dois casos.

**Formato do arquivo.** `formato` e `versao` vêm primeiro e são conferidos primeiro. Arquivo de outra ferramenta, sem versão, ou de versão **mais nova** que a que está rodando é **recusado com explicação** — meia configuração entrando em silêncio é o defeito que este projeto mais evita.

```
{ formato:"construtores-fotocerta", versao:1, tipo:"tudo"|"preset", dados:true|false,
  geradoEm:"<ISO>", presetsGerais:[...], presetsDeAba:{abaId:[...]},
  rascunho:{<estado das seis abas>}, rascunhoGeral:{ativo,ativas,origens,codigos} }
```

- **O rascunho sai do mesmo `fcEstadoAtual()` que grava o armazenamento.** A função foi extraída de `salvarEstado` nesta fase justamente para isso: montar o estado por fora seria uma segunda montagem, e duas montagens divergem — e aqui a divergência apareceria como *"o backup não traz o que a ferramenta tem"*.
- **A biblioteca de presets não viaja duas vezes.** Ela é retirada do `rascunho` (`<pref>.presets`) porque vai em `presetsDeAba`. Duas cópias da mesma coisa no mesmo arquivo divergem no dia em que uma delas for filtrada.
- **`rascunhoGeral` anda junto do rascunho**, porque é a mesma coisa que ele — o que está na tela: qual preset está selecionado, quais abas estão ligadas, as marcas de origem e os dois "Outros códigos meus". Por isso só é restaurado quando o operador manda aplicar o rascunho.

**O arquivo importado é entrada NÃO CONFIÁVEL — a mais perigosa que esta ferramenta já teve**, porque um JSON vira configuração e a configuração vira código publicado no site do cliente. Ele não pode ser tratado como o `localStorage`, que é do próprio operador. Três camadas, nesta ordem:

1. **Forma** (`fcxSanear` / `fcxConformar`): tipo, tamanho de texto, comprimento de lista, profundidade, quantidade de chaves e nome de chave. **`__proto__`, `constructor` e `prototype` ficam de fora antes de tudo** — este bloco copia valores por atribuição de chave, e atribuir `__proto__` num objeto comum troca o protótipo em vez de criar um campo. **O molde do que se conhece é o `coleta()` da própria aba** (`fcPresetCapturar`), não uma segunda lista de campos: chave que não existe na aba não entra, e é contada. **Lista vazia não abre buraco no molde**: cada lista das abas declara em `ABAS` um `[caminho, molde de um item, chave essencial]`, e `fcxSemearListas` planta o item de exemplo onde a lista do operador está vazia — sem ele a conferência caía no saneamento genérico, que só sabe de forma e por isso aceitava `null`, número, objeto e lista dentro de uma lista de textos, **sem contar nada**. O caminho atravessa lista (`u.prods.ops`) porque um produto sem opcionais deixa o molde de dentro vazio pelo mesmo motivo.
2. **Regra da aba**: o gancho `importar` do registro `ABAS`. Hoje só o Slideshow tem uma — endereço de foto que não passa em `sUrlOk` **não entra na lista**, porque `url` é o único campo que vira `src` e sai dentro de `IMAGENS[].url` no bloco entregue. O cadastro manual recusa isso desde a fase 4 anterior; o arquivo não podia ser a porta dos fundos. **O gancho não é mais o único lugar que conta descarte de lista**: `fcxPodarListas` roda antes dele, nas seis abas, pelos mesmos caminhos declarados.
3. **Travas que já existem**: aplicar passa pelo `restaura()` da aba (`corValida`) e pelo `redesenhar()` (`fcAjustarTodos`); gerar passa por `corSegura`, `urlLimpa`, `escHtml`, `escAttr` e `escJs`. **A importação não cria caminho novo de escrita de campo.**

**A data do arquivo é ecoada na confirmação, então ela é texto de arquivo aparecendo na tela.** Vai por nó de texto (a pergunta de três saídas nunca usa `innerHTML`), o que fecha a marcação — mas não fecha o resto: um arquivo hostil poria ali uma **frase**, e uma frase no meio de uma confirmação que o operador está lendo para decidir é capaz de mentir. Medido com `geradoEm: "ATENCAO: nenhum preset sera substituido, pode confirmar"`. O campo passou a ser aceito só na forma de data ISO; qualquer outra coisa vira *"em data desconhecida"*. **O arquivo pode escolher a data, nunca o texto.**

**Nunca sobrescreve calado: duas perguntas, e só depois de as duas terem resposta é que alguma coisa é escrita** — assim cancelar no meio não deixa metade importada.

1. **O resumo**, com os números que o R4 pede (*"3 presets gerais novos, 2 que já existem (serão substituídos), 7 presets de aba novos"*), mais o que foi descartado e o que foi encurtado. Havendo colisão de nome, é aqui que se escolhe entre **substituir** e **importar como cópia**; não havendo, o botão é só *Importar*.
2. **O rascunho**, que substitui a **tela** — a decisão mais destrutiva do fluxo. Havendo alterações não salvas no preset geral ativo, elas são listadas uma a uma, com o mesmo `fcgMotivos` da fase 3.

**Importar como cópia renomeia, e o renome é o mesmo da leitura do armazenamento.** Preset geral colidente ganha número na **campanha** (`fcgCampanhaLivre` → `Natal 2026 (2)`) e preset de aba ganha número no nome (`fcxNomeLivre`). Isso é deliberado: a fase 3 fechou um defeito em que um par `(campanha, página)` repetido produzia um preset **invisível e indelével**, e registrou que o "importar como cópia" prometido pelo R4 era justamente quem poderia produzi-lo. Ele não produz — a cópia troca a campanha antes de entrar, e o par continua único por construção.

**Arquivo "sem dados" NÃO apaga os dados atuais.** O que o "sem dados" faz é **omitir a chave**; na importação, campo omitido **herda** o que já existe — do preset que está sendo substituído, ou da tela, quando o preset é novo. Campo **presente e vazio** não herda nada: vazio é escolha, e a regra desta ferramenta é honrar o vazio no texto livre. É por isso que a exportação apaga a chave em vez de gravar `''` — a diferença entre *"o arquivo não trouxe"* e *"o arquivo trouxe vazio"* é a **ausência**. Medido: preset geral substituído por um arquivo sem dados, com um campo não-operacional mudando de valor para provar que a substituição aconteceu, e os **seis** campos operacionais intactos.

**Aba em só-leitura não recebe nada, e o que ela já tinha guardado é preservado.** A aba que falhou ao restaurar parou de coletar do DOM: ela não serve de molde nem pode ser escrita. A confirmação nomeia essas abas. E ao **substituir** um preset geral, a entrada daquela aba dentro do preset fica **exatamente como estava** — escrever o vazio por cima apagaria a configuração dela por causa de um defeito de outra aba, sem ninguém nomear.

**Se o preset que o arquivo dizia estar selecionado não veio junto, a barra cai no Rascunho — e diz.** Junto vão os dois "Outros códigos meus": o Rascunho não é uma página, e dali eles seriam levados para a próxima página criada, que é o vazamento entre campanhas que a fase 3 fechou. Backup tirado **no** Rascunho (`ativo` nulo) é o caso oposto e os mantém: ali foram digitados sem página nenhuma.

**Uma mensagem não pode dizer as duas coisas.** As linhas *"o rascunho foi aplicado"* e *"o rascunho NÃO foi aplicado"* são um par de opostos, e a linha do "caiu no Rascunho" inserida **entre** as duas fez o `senão` passar a pertencer a ela: a mesma mensagem afirmava as duas. Medido na verificação como operador. O acréscimo independente fica **depois** do par.

**Valor de arquivo não entra em seletor CSS — e o conserto foi no ajudante, não no chamador.** `setRadio` interpolava o valor dentro de `input[name="..."][value="..."]`; uma aspa dupla fechava a string e `querySelector` lançava `SyntaxError`. Medido com um arquivo cujo **único** campo envenenado era `c.fonte = 'neutra" i]'`: `cRestaura` parava no meio, a Contagem caía em só-leitura e a aba ficava **escrita pela metade** — `c-cod` mostrando `NATAL26BARRA` na tela enquanto o armazenamento ainda tinha `""` —, e o mesmo valor dentro de um preset geral relançava a cada seleção. `setRadio` passou a usar `getElementsByName` e comparar em JavaScript: o valor volta a ser só texto. **Um ajudante, 67 grupos de rádio protegidos** (59 deles são os que o estado realmente escreve; os outros 8 são formulários de cadastro e o importador de galeria, que nunca foram restaurados — igual em `main`). Conferido par a par: nos 175 rádios da página, o seletor antigo e a busca nova apontam para o **mesmo** elemento, e valor desconhecido continua não mexendo em nada — de propósito, porque o `l-corujapos` depende disso.

**Casca não é item.** A conferência contra molde perdoa **chave ausente** de propósito (é o que mantém válido o estado gravado por versão anterior depois de a aba ganhar campo novo), e perdoando a ausência ela deixava sobrar o objeto vazio: `{"texto":"obj"}` na lista de opcionais perdia `texto` por ser chave desconhecida, virava `{}` e chegaria ao bloco publicado como um opcional chamado `undefined`. Por isso a declaração da lista traz a **chave essencial** — `url` na foto, `nome` no produto e no opcional, `codigo` no cupom, `texto` na mensagem —, e `fcxPodarListas` recusa e **conta** quem não a tem. Medido com `l.qops = [null, 1, {"texto":"obj"}, ["a"], "opcao boa"]` e lixo equivalente nas outras listas: antes, **8** descartes anunciados e `var PERGUNTA_OPCOES=['null','1','[object Object]','a','opcao boa']` no bloco gerado; depois, **26** descartes e `var PERGUNTA_OPCOES=['opcao boa']`. De quebra, as abas Checkout e Contagem deixaram de cair em só-leitura: os itens que faziam o desenho da lista estourar já não chegam nelas.

**Foto de host de fora entra, mas não entra calada.** `sUrlOk` é agnóstica a host de propósito — o cadastro manual aceita foto hospedada em outro lugar —, e a decisão continua sendo a da fase 2.5: **avisar sem recusar**, com o host em destaque no cartão da lista. O que muda num arquivo é de quem veio o endereço: num preset recebido de outra pessoa ele não foi digitado por ninguém desta casa, e um endereço de terceiro no meio de 46 passa por foto normal. A confirmação passou a dizer **quantas** são, antes de o operador decidir, e o recado que fica na tela repete o número. A contagem é de **endereços distintos** (`conta.forVistas`), como no importador de galeria: a mesma foto no rascunho, num preset geral e num preset de aba é **uma** foto de fora, não três.

**Sem servidor, e sem travar.** Baixar é `Blob` + `URL.createObjectURL` + `<a download>` (o `<a>` entra e sai do documento, porque o Safari não dispara o clique de um elemento fora da página, e o endereço temporário é devolvido depois). Ler é `<input type="file">` + `FileReader`. Os tetos — 8 MB de arquivo, 200 000 caracteres por caixa de código manual, 20 000 por texto de campo, 1000 itens por lista, 200 chaves por objeto, profundidade 7, 60 000 nós — existem para que arquivo enorme, fundo ou hostil não trave nada, e são folgados: o backup completo medido — 46 fotos, 6 produtos com 18 opcionais, 5 cupons, 5 mensagens e três presets em cada uma das seis bibliotecas — dá **~91 KB** (o armazenamento dela são 59 KB; o arquivo é maior porque sai indentado). O número anda **com o que há dentro dele**: “a maior configuração” sem dizer qual não dá para conferir, e foi por isso que este parágrafo e o comentário dos tetos no `index.html` chegaram a dizer ~25 KB e ~120 KB sobre o mesmo backup. Medido de novo, um número só, nos dois lugares.

**Espaço de nomes `fcx-`**, pelo mesmo motivo de `fcp-` e `fcg-`: campo de aba começa por prefixo de **uma** letra, então não pode colidir nem ser alcançado pelos listeners de "mudou alguma coisa nesta aba". `fcx-` e não `fcb-` de propósito — `fcb-` é o prefixo das classes que a Contagem regressiva escreve no **código gerado**, e um grep por ele traria as duas coisas misturadas. Varredura de IDs repetidos: `[]`, com 403 IDs no armazenamento limpo (398 antes; os cinco novos são todos `fcx-`).

**Exportar e importar é TRANSPORTE: não pode mudar o que sai.** As 9 saídas dos seis geradores foram comparadas byte a byte (SHA-256) com as de `main`, em cenário com preset geral e sem, e a **ida-e-volta** — exportar tudo, limpar o armazenamento, importar de volta — devolve as mesmas 9 saídas e o `fcConstrutores` com o **mesmo hash**. Refeito depois da rodada de correção, com 46 fotos, 6 produtos com 18 opcionais, 5 cupons, 5 mensagens e três presets em cada biblioteca: as 9 saídas e o `fcConstrutores` batem com os de `main` nos dois cenários, e a ida-e-volta devolve os dois armazenamentos com o mesmo hash e **zero** descartes. O campo `b.consol` (a consolidação do código 1 das Bordas) faz parte dessa prova: ele é `fora` do preset, mas é do **rascunho**, e por isso `fcPresetCapturar` ganhou o sinalizador `manterFora` — sem ele o molde descartaria `consol` como chave desconhecida e o código 1 voltaria de um backup sem a consolidação que tinha.

### Painel consolidado (ago/2026, fase 5) — selecionar tudo e colar, em vez de procurar onde o bloco começa

Para trocar um bloco na Tag Head o operador precisava achar onde aquele bloco começa e termina no meio do campo. Errar apaga o bloco vizinho — foi o que custou tempo real na correção das bordas da landing de Natal. O painel, na faixa à direita das abas, entrega **o campo inteiro**: seleciona tudo e cola.

**Ele junta dois campos e só dois.** Tag Head e Tag Body são campos **da página**. Slideshow, Checkout, TidyCal (saídas 1 e 3) e o código 2 das Bordas vão para **componentes individuais**, cada um com o campo só dele: não há o que consolidar. O painel os **lista**, com o botão de copiar de cada um, e nunca os junta. A Contagem regressiva cai nos dois lados, conforme o radio *fixa no topo* (Tag Body) ou *no fluxo* (componente) — o painel acompanha a escolha, lida dos valores da aba e não do DOM, para que aba em só-leitura entregue o que estava gravado.

**Ele não é um gerador.** `fccRender` lê as caixas de código que os seis geradores escreveram e as junta; nenhuma linha do painel monta bloco. Se ele pudesse formatar código, seria uma segunda implementação do gerador — o defeito que a prévia da Contagem regressiva pagou duas vezes. Prova: as **9 saídas** continuam byte a byte idênticas às de `main`.

**Só abas ativas entram.** É a razão de ser do R2 da fase 3: sem ele, selecionar *Natal — Embutida* montaria uma Tag Body com o bloco de captação de leads dentro, numa página que não deveria tê-lo — o painel pareceria funcionar e entregaria errado. Medido: com o Checkout **fora** e 22 107 caracteres de código gerado na caixa dele, o painel não o menciona em lugar nenhum; ligado o interruptor, ele aparece na lista de componentes.

**Falta código gerado, o campo não é montado.** Aba ligada cuja caixa está vazia (é o estado de toda aba logo depois de recarregar a página) faz o painel dizer *qual* bloco falta e *qual botão* apertar, em vez de montar um campo incompleto que parece completo. Caso diferente é o código **gerado antes** de a aba mudar: aí o campo é montado e um aviso âmbar nomeia as abas que mudaram depois. Quem sabe isso é `fccGerado`, uma assinatura dos valores da aba anotada no fim de cada gerador — anotação ao lado, que não toca no que o gerador emite.

**A assinatura de frescor não é a do preset geral, e a diferença é proposital.** Os campos `fora` (hoje só `b.consol`, a consolidação do código 1 das Bordas) descrevem **outro** componente: por isso não viajam com o preset nem são sobrescritos ao aplicar um. Mas `b.consol` **muda o que a aba emite** — é ele que manda o código 1 carregar também o `@keyframes` do outro componente. Assinar sem ele deixava a caixa envelhecer **calada**: medido, escolher um preset na caixa de consolidação leva `b-out1` de **563 para 850 bytes** e a Tag Head montada de **645 para 932** — 287 bytes, a animação inteira do outro componente — e o painel continuava oferecendo a Tag Head antiga como "conteúdo completo", sem uma palavra; colar isso publica a página com o segundo componente sem animação de borda. `fccAssinar` acrescenta os campos `fora` à assinatura por `fcPresetCapturar(a,true)` — o mesmo caminho único de captura, só que sem descartar esses campos —, e só nas abas que têm campo `fora` (uma). Quem lê o **preset** continua sem enxergá-los.

**Dois estados em que o aviso de código velho estaria mentindo, e o que o painel faz neles.** *Caixa esvaziada:* mexer na lista de fotos apaga a caixa do Slideshow (`sSaidaVence`), e o painel dizia *"o que está abaixo é o código antigo"* logo acima de *"Ainda não gerado"*. `fccTemCodigo` tira do aviso a aba cuja caixa está vazia — caixa vazia não tem código velho, tem código nenhum, que é o caso mais forte e já é dito no próprio campo. *Aba em só-leitura:* ali o gerador leu o **DOM** e `fcgValoresDaAbaLer` devolve o **fragmento guardado**, então a comparação seria entre duas coisas que nunca foram feitas para bater — `fccAssinar` devolve `null` e a aba sai da comparação. Em troca ela é **anunciada**: o painel repassa, com as palavras da própria aba, que ela *não grava nada até a página ser recarregada*, em vez de mandar "abra a aba e clique em Gerar código" — um passo que naquele estado não resolve.

**A ordem dentro do campo, e as duas linhas de comentário.** Linha de identificação → "Outros códigos meus" (R5) → linha de fronteira → blocos gerados. A fronteira só sai quando existe bloco depois dela: sem essa guarda, um campo com código manual e nenhuma aba ligada terminava anunciando *"daqui para baixo, gerado pelos Construtores"* com nada embaixo.

> **As duas linhas vão como comentário de HTML, e não de CSS.** A spec as escreveu no formato `/* … */`. Os campos Tag Head e Tag Body do Prosite recebem **HTML** — a própria Tag Body aceita `<style>` e `<script>` —, e o que estiver fora dessas tags é texto. Medido com o analisador do navegador: `/* Construtores Foto Certa -- … */` no começo de um corpo vira um **nó de texto** (`nodeType` 3), ou seja, sairia **impresso na página publicada**. Na forma `<!-- … -->` vira comentário (`nodeType` 8) e nada aparece.

**O nome da campanha entra saneado.** `fccSeguro` tira `<` e `>`, colapsa hifens repetidos e remove acentos (regra 10 do Manual do Prosite). Sem `>` nenhuma sequência de fechamento de comentário pode se formar dentro do nome, então o comentário não termina antes da hora e não despeja o resto como texto visível. Medido com a campanha renomeada para `Páscoa --> <b>x</b> -- 2027`: a linha sai como `<!-- Construtores Foto Certa -- Pascoa - bx/b - 2027 -- pagina HOSPEDEIRA -- Tag Head -->` e o analisador devolve **um** comentário, seguido só de espaço em branco e dos `<style>`.

**Colisão de animação salta aos olhos.** Dois componentes com o mesmo efeito de borda colidem: as animações se chamam igual e vale a última. A consolidação do código 1 (aba Bordas) recusa o caso que ela enxerga — dois presets desta ferramenta. O que ela **não** enxerga é o bloco que o operador colou à mão e guardou em "Outros códigos meus": com o painel, esse bloco e o gerado ficam lado a lado no mesmo campo, e a colisão passa a ser detectável. Critério: nome de `@keyframes` declarado em **dois blocos** diferentes colide; dentro de um mesmo bloco, **duas** declarações do mesmo nome são normais (é o par "animação + redefinição sob `prefers-reduced-motion`" que todos os blocos emitem), e a partir da terceira o painel avisa igual. Medido: `fc-borda-giro` colado à mão contra `fc-borda-brilho` gerado → nenhum aviso; trocado o nome do colado para `fc-borda-brilho` → caixa vermelha nomeando a animação e os dois blocos.

**A saída do TidyCal em modo embutido pertence a duas páginas, e o painel sabe disso.** As saídas 1 (componente do TidyCal) e 2 (Tag Body) são da página **Embutida**; a saída 3 (o iframe) é da **Hospedeira**. Com *Natal 2026 · Hospedeira* selecionada, a saída 3 vai para a lista de componentes e as saídas 1 e 2 vão para a seção **"É de outra página desta campanha"**, com a instrução de selecionar o preset daquela página. Nada some; o que não é desta página não entra nos campos dela. Juntar a Tag Body da intermediária dentro da Tag Body da hospedeira é exatamente o erro que a linha de identificação existe para denunciar *depois* — aqui ele não chega a acontecer.

**O aviso do risco fica no ponto de cópia, não na documentação.** Ao lado de cada botão Copiar, em vermelho: *"Este painel só conhece o que está aqui. Se a sua Tag Body tiver código que você colou à mão e não está na caixa de códigos manuais, colar isto apaga aquilo."* O painel entrega o campo **inteiro**; é o único risco desta fase que não tem conserto automático.

**Quando ele se redesenha.** Dentro de `fcgAtualizar`, no mesmo `try` da barra do preset geral: quem acorda os dois é o `salvarEstado`, por onde toda mudança de valor passa — inclusive as que vêm de clique em botão e não disparam `input` nem `change`. Mais um agendamento próprio (250 ms, timer único) disparado por `fccMarcar` no fim de cada gerador. Uma **assinatura** do desenho e do conteúdo das caixas evita refazer o `innerHTML` à toa: sem ela, cada tecla digitada em qualquer aba mataria uma seleção em andamento — e selecionar tudo para copiar é justamente o gesto que este painel existe para servir.

**Espaço de nomes `fcc-`**, pelo mesmo motivo de `fcp-`, `fcg-` e `fcx-`: campo de aba começa por prefixo de **uma** letra, então `fcc-…` não colide com campo nenhum e não é alcançado pelos listeners de "mudou alguma coisa nesta aba".

### A faixa da ferramenta e o número de colunas (ago/2026, fase 5)

Até aqui tudo era **1080 px fixos e centrados**: num monitor 2K sobravam **732 px de areia em cada lado**. Era o achado D do dono, e ele veio junto do painel com um enunciado que virou restrição: *"o ajuste já passará a contar com o painel consolidado usando parte da área à direita das abas"*.

- **Quem tem teto é a coluna, não a faixa.** A primeira versão desta fase pôs o teto na **faixa** (`--larg:1980px`) e mediu as colunas dentro dele — e caiu no achado D outra vez, só que menor: no monitor do dono (2560 px) sobravam **283 px de areia de cada lado**, medidos. Hoje o teto é da **área das abas** (`--abas:1536px`, a largura já equilibrada em duas colunas de 735 px) e o que passa disso vai para o painel consolidado, `clamp(380px, calc(100% - 1536px - 24px), 900px)`, em vez de virar areia. `--larg` é a soma (20 + 1536 + 24 + 900 + 20 = **2500 px**): até 2500 px de janela não há areia nenhuma, e a 2560 sobram **23 px de cada lado** contra 283. Medido a 2560: abas 1536, painel 900, colunas 735 — as mesmas de antes.
- **Por que a sobra vai para o painel, e não para a coluna.** O painel é **código**: com 380 px cabem ~54 caracteres por linha de `<textarea>` em 11 px monoespaçado, e a rolagem lateral aparece justamente na caixa de onde se **copia**; com 900 px cabem ~140. A coluna de fieldsets, ao contrário, não ganha nada em passar de 735: medido sem teto nenhum a 2545 px, a coluna vai a **1017 px** e a aba mais alta encolhe **2,5 %** (Leads 5300 → 5170), enquanto as linhas dos `<p class="ajuda">` dentro dos fieldsets — que não têm teto próprio como `.descricao` e `.instrucoes` têm — passam de ~170 caracteres.
- **As abas não vão até a borda.** A largura delas é o que sobra depois do painel — literalmente `flex:1 1 auto` ao lado de um `flex:0 0 clamp(...)`, e é o `clamp` que garante que isso nunca passe de 1536 px.
- **A 1400 px nada mudou.** A faixa dividida ainda dá 941 px para as abas e 380 para o painel, com colunas de 437,5 px — os mesmos números da versão anterior, porque abaixo de ~1960 px de janela a sobra não chega aos 380 px e o `clamp` devolve o mínimo.
- **Abaixo de 1400 px a faixa deixa de ser dividida** e o painel cai **abaixo** das abas, que voltam a ter a largura inteira. O painel é o segundo filho de `.app` justamente para isso: o empilhamento não precisa de nenhuma regra de reordenação. O corte não é redondo por acaso — a 1400 px a coluna de fieldsets ainda mede 437,5 px (445 sem a barra de rolagem), acima do mínimo de 360 px declarado em `.grade`; abaixo disso a segunda coluna começaria a ser espremida.
- **A regra do número de colunas, sem eufemismo: 1 ou 2, nunca 3.** As **30** `.grade` das seis abas têm exatamente **dois filhos** cada uma — dois cartões que empilham os fieldsets agrupados por tema —, e `repeat(auto-fit, …)` nunca abre mais faixas do que há itens. Então a regra real é *"1 coluna abaixo de ~744 px de container, 2 acima"*, em largura nenhuma 3. Dizer que o número de colunas é "conta do container" é verdade pela metade e sugere uma flexibilidade que não existe: o container manda em 1-ou-2, nunca em 3. O que o `auto-fit` resolve de fato — e por isso continua — é **medir a própria grade**, que na faixa dividida já é "o que sobra depois do painel"; era isso que a `@media (max-width:840px)` não sabia fazer, e ela saiu.
- **`min(360px,100%)` e não `360px`:** numa janela estreita a faixa mínima de 360 px estouraria o container e devolveria a rolagem horizontal que a fase 2.5 acabou de tirar. Medido a 360 px de janela: `scrollWidth` = `clientWidth` = 360.
- **Uma terceira coluna foi medida e recusada, com números.** Os dois cartões de cada `.grade` guardam de **2 a 7** fieldsets (o pior caso é a primeira seção do Checkout, 4+3). Forçando os cartões a `display:contents` — que promove cada fieldset a item da grade e libera o `auto-fit` — a 2545 px sem teto: a coluna cai de 1017 para **670 px** e as abas encolhem de **5 a 14 %** (Leads 5170 → 4827, Contagem 4434 → 3895, Bordas 3122 → 2810, Checkout 4371 → 4050, Slideshow 3187 → 3010, TidyCal inalterada). O preço, medido na mesma passagem: o número de colunas passa a variar **dentro da mesma aba**, seção a seção, porque cada `.grade` tem uma contagem diferente — a Contagem regressiva sai com **3, 2, 4, 5, 2 e 3** colunas, de 392 a 1017 px de largura —, e a seção *Prévia e código gerado* do TidyCal desaba para **uma** coluna de 2059 px, ou seja a prévia deixa de ficar ao lado do código. Trocar ~8 % de altura por isso não paga. Uma terceira coluna honesta exigiria reagrupar à mão os fieldsets das 30 seções, o que é outra tarefa — e contraria o padrão de layout que esta documentação manda seguir. Por isso o espaço que sobra vai para o painel consolidado e para a lista de imagens em largura inteira, e não para uma coluna a mais.
- **Quando o painel vai para o fim da página, o alto da aba avisa.** Abaixo de 1400 px o painel deixa de dividir a faixa, e a 1280 px ele começa **3753 px abaixo do topo** — ninguém rola até lá sem saber que existe algo lá. Uma faixa `.fcc-atalho`, visível só nessa largura, fica no alto de `.app-esq` (onde o operador já está olhando) com o botão *Ir para o painel*.
- **O painel "Detalhes" do preset geral acompanha a faixa.** Ele era 1080 px cravados e centrados na **janela**, alinhado com nada: medido a 2000 px, a barra ia de 3 a 1983, as abas de 23 a 1559 e os fieldsets de Detalhes de 453 a 1533. Hoje a `.grade` dele usa o mesmo `max-width:var(--larg)` e a mesma folga de 20 px da `.fcg-linha`, e começa e termina onde a barra começa e termina. Aqui a media query é legítima (`@media (min-width:840px){grid-template-columns:1fr 1fr}`) porque `.fcg-painel` ocupa a **janela** inteira — e ela é necessária: essa grade tem **três** filhos (os dois cartões mais a caixa larga de exportar/importar) e sem ela o `auto-fit` abriria uma terceira faixa vazia assim que coubesse.
- **A lista de imagens do Slideshow ocupa a largura inteira da aba**, abaixo dos parâmetros da seção 1 (pedido explícito do dono). Ela ficou **fora** de qualquer `.grade`: um `<div>` solto já é bloco de largura cheia, sem depender de span de grade nem de faixa vazia. A seção 1 passou a ser *Adicionar imagem + Importar uma galeria inteira* à esquerda, *Como as fotos entram na lista* à direita, e a lista embaixo.
- **O teto de 520 px da lista sobrevive à mudança, e a justificativa foi refeita, não copiada.** Medido com a lista em **1460 px** de largura: o cartão continua com **96 px** (a altura vem da miniatura de 64×44 e das linhas fixas, não da quebra do texto), então 520 continua sendo exatamente 5 cartões inteiros; e da linha da contagem até a base do botão *Limpar lista* vão **596 px** = 520 + 76 de moldura, os mesmos números da fase 2.5. A 700 px de janela o cartão também mede 96 px.
- **Texto corrido não acompanha a faixa.** `.descricao` e `.instrucoes` ganharam teto de **1100 px**: a 1536 px e 13 px de fonte a linha passaria de 250 caracteres. Os fieldsets continuam usando a largura inteira, porque ali a linha é curta por natureza.
- **`fieldset{min-width:0}` e o mínimo zero das faixas continuam de pé** — são o que impede o endereço de uma foto de empurrar a coluna, e a fase 2.5 os pagou caro. O `minmax(0,1fr)` virou `minmax(min(360px,100%),1fr)`, que tem o mesmo efeito quando o espaço aperta.

**O estouro de 11 px da barra de abas a 700 px já estava fechado.** A pendência registrada na fase 2.5 foi reproduzida no commit daquela fase (`a77c16a`): a 685 px de largura útil, `aba-cnt` terminava em **696** e o `scrollWidth` da página ia a 696 contra 685. O que a fechou foi o `flex-wrap:wrap` que a **fase 3** acrescentou a `.abas` por causa dos selos "fora". Medido em `main` e na fase 5, a 700 e a 685 px, com e sem os selos: `scrollWidth` = `clientWidth`, e o último botão termina dentro da caixa (620 de 680 a 700 px; 610 de 665 a 685 px, com cinco selos e três linhas de botões).

**Teto de 100% nas quatro molduras de prévia.** A largura da moldura é escrita em pixels na hora de montar, com a largura que a coluna tinha naquele instante, e a prévia só é remontada ao abrir a aba ou ao clicar em *Atualizar prévia*. Encolher a janela depois disso deixava a moldura maior que a coluna e a **página inteira** ganhava rolagem horizontal — medido em `main`, com a prévia montada a 2560 px e a janela levada a 400: `scrollWidth` 513 contra `clientWidth` 400. É pré-existente, mas a fase 5 alargou as colunas e trouxe o mesmo defeito para 700 px, que é largura de uso. Com `max-width:100%` a moldura encolhe junto e o excesso é cortado pelo `overflow:hidden` que já estava lá: prévia cortada em vez de página torta.

### Padrão de layout das abas (seguir sempre, inclusive em abas novas)

Toda aba tem o mesmo fluxo linear, de cima para baixo:

0. **Interruptor do preset geral** (`<div class="fcg-int">`, montado por `fcgIntMontar`) — só existe quando há preset geral selecionado, e nesse caso é o **primeiro** elemento do painel, antes da descrição. Diz se a aba faz parte da página e permite ligar/desligar. Não é uma seção numerada: é o cabeçalho de contexto da aba, e some no Rascunho.
1. **Descrição** (`<p class="descricao">`) — o que o construtor faz, em um parágrafo.
2. **Seções numeradas de configuração** — cada uma abre com `<div class="secao"><span class="secao-n">N</span> Título</div>` (a primeira leva `class="secao primeira"`, que remove a linha divisória do topo) e é seguida por `<div class="grade">` com **duas caixas** de `<fieldset>` — que viram duas colunas quando há espaço e uma só quando não há, por conta do `auto-fit` (ver "A faixa da ferramenta e o número de colunas"). Agrupar por tema, distribuindo os fieldsets entre as duas caixas para equilibrar a altura; quando houver formulário de cadastro + lista (produtos, cupons), o formulário fica à esquerda e a lista à direita. **Lista que cresce sem limite** — hoje só a de imagens do Slideshow — fica **fora da grade**, em largura inteira, abaixo dos parâmetros da seção.
3. **Penúltima seção: "Biblioteca de presets"** — só o cabeçalho e um `<div class="grade" id="fcp-<pref>-box"></div>` vazio ficam no HTML; os dois fieldsets são montados por `fcPresetsMontar`, igual nas seis abas (ver a seção seguinte). O `fcp-` não é enfeite: é o espaço de nomes que impede a biblioteca de colidir com campo de aba (ver "Esquema de ID" na seção anterior).
4. **Última seção: "Prévia e código gerado"** — botões de ação (`Gerar código` e afins) numa `<div class="acoes">` logo abaixo do cabeçalho da seção, depois uma `grade` com a prévia (`<div class="pv-area">`) à esquerda e a(s) saída(s) (`<div class="saida">` com textarea + botão Copiar) à direita. Abas sem prévia (TidyCal) usam a mesma seção só com as saídas.
5. **Instruções ao final** (`<div class="instrucoes">`), em largura total: onde colar, pré-requisitos, como funciona e o que fazer depois de publicar.

Dentro dos fieldsets: `radios` para valores de lista fechada, campos com `<small>` explicando unidade/limites, e `<p class="ajuda">` para orientações. Prefixo de ID por aba (`s-`, `l-`, `t-`, `u-`, `b-`, `c-`, `p-`) em todos os campos, e o mesmo prefixo nas funções JS correspondentes.

**Lista de dezenas de itens: quatro regras que a fase 2.5 (ago/2026) firmou.** O importador de galeria tornou comum a lista de 46 fotos, e o layout que nunca tinha sido desenhado para isso apareceu inteiro numa captura do dono.

- **Nada pode ficar preso na largura de um texto sem ponto de quebra.** O endereço de uma foto do storage tem 150+ caracteres e nenhum espaço, e `text-overflow:ellipsis` só age se algo lá em cima obrigar a encolher — o que não acontecia por dois motivos ao mesmo tempo: o `<fieldset>` nasce com `min-inline-size:min-content` (corrigido com `fieldset{min-width:0}`) e a regra de coluna única abaixo de 840 px usava `1fr` em vez de `minmax(0,1fr)`, cujo mínimo automático também é o `min-content`. Medido com as 46 fotos: coluna de 507 px contra fieldset de 1253 px na janela larga (o cartão atravessava a borda e invadia a coluna vizinha), e faixa de 1299 px numa janela de 700 px (barra de rolagem horizontal na página inteira). **Essas duas regras — e só elas — valem para toda a ferramenta**, porque moram no `fieldset` e na `.grade`: com um texto de 113 caracteres sem espaço, os fieldsets das opções de Leads e das mensagens da Contagem saíram de 762 e 804 px para 507 px, e a página deixou de ter rolagem horizontal (1406 e 1448 → 1265, numa janela de 1280). Produtos e cupons ganham o mesmo pelo mesmo motivo.
- **Uma linha só é regra do `.url`; o corte no meio é variante de uma lista só.** Quatro renderizadores usam `.url`: três põem o texto **direto no `<div>`** (opções de Leads em `lQRender`, texto e recado curto da Contagem em `cMsgRender`) e um monta caixas filhas (`sRender`). A primeira versão da fase 2.5 pôs `display:flex` no `.url` comum e mudou `white-space/overflow/text-overflow` para `.url span` — e nas três listas de texto solto o texto virou **item de flex anônimo**, que não aceita `text-overflow`: medido a 1280 px, uma opção de 113 caracteres sem espaço saía com 672 px de conteúdo em caixa de 417 (255 px pintados por cima do cartão, e rolagem horizontal na página), e com espaços quebrava em **duas linhas**. A correção é dividir: `.url` sozinho carrega `white-space:nowrap; overflow:hidden; text-overflow:ellipsis` (vale para as quatro), e só o slideshow acrescenta `.partida`, que é onde `display:flex` e os filhos vivem. O corte no meio existe porque o começo do endereço (esquema, host, pasta da galeria) é igual nas 46 fotos e não identifica nada — `.pasta` (`flex-shrink:200`) some antes de `.arq` (`flex-shrink:1`) começar a ser cortado, e o endereço completo fica no `title`. **A pasta não colapsa a zero:** `min-width:1.1em` deixa espaço para o próprio `text-overflow` dela desenhar o `…`, que é o marcador de que houve corte **à esquerda** (a reticência do fim não diz isso). Limite honesto: os 46 nomes reais ficam distintos porque trazem data e número no começo, mas **arquivos que compartilhem um prefixo longo e só difiram no fim continuam com textos visíveis iguais** — nesse caso quem resolve é o `title`. Cuidado ao mexer: o critério de corte é a **última barra do caminho**, não do endereço inteiro — uma barra dentro da query faria o "nome do arquivo" nascer sem o nome do arquivo.
- **Área de rolagem própria, com o item movido acompanhando.** `.lista-rolagem` (hoje só o `#s-lista`) tem teto de **520 px = exatamente 5 cartões inteiros** (96 px de cartão + 8 px de respiro) — o item movido mais **quatro** vizinhos. Os quatro não ficam dois de cada lado: `sListaVer` alinha pela **borda**, então descendo o item para na base (quatro acima) e subindo para no topo (quatro abaixo); nos dois casos são as posições por onde ele acabou de passar. Com 46 fotos a seção 1 caiu de **5563 px para 1413 px**. Duas obrigações vêm junto: `sRender` **guarda e repõe o `scrollTop`** — quem precisa disso são `sDel` e `sMove`, os dois caminhos que redesenham com a lista rolada (`sLegEdit` **não** chama `sRender`) —, e `sMove` chama `sListaVer(destino)`, que rola **só o container** por conta de `offsetTop`; `scrollIntoView` rolaria também a página, devolvendo a lista ao preço de a aba saltar debaixo do operador.
- **O teto acompanha a altura da janela.** O invariante que o teto sustenta é *a linha da contagem e o botão “Limpar lista” cabem na mesma tela*, e ele depende da janela: da contagem até a base do botão vão o teto mais 76 px de moldura. Medido com 46 fotos — 5 cartões ocupam 596 px, 4 ocupam 492, 3 ocupam 388 —, numa janela de 600 px o teto de 5 sobrava **4 px**, folga que some no primeiro arredondamento. Em vez de o limite ficar só escrito aqui, duas `@media` derrubam o teto para 416 px abaixo de 620 e para 312 px abaixo de 520, sempre em cartões inteiros e com o corte **acima** do que cada teto precisa. Limite que resta, dito por inteiro: **abaixo de ~388 px de altura de janela o invariante não se sustenta com teto nenhum**, porque a moldura sozinha já passa disso.

**Ação destrutiva em lista tem confirmação com número.** *Limpar lista* (fase 2.5) diz quantas fotos serão removidas, diz que as configurações da apresentação ficam e que **nenhum código já colado no site é afetado** — mesma redação da remoção de preset. O botão nasce desligado com a lista vazia, e a linha `.lista-conta` acima da lista existe para o número da confirmação poder ser conferido **antes** do clique: com área de rolagem o operador deixa de ver o fim da lista. Não confundir com *Limpar tudo* (`sLimpar`), que devolve a aba inteira aos padrões.

**Mudou a lista, a caixa de código esvazia (`sSaidaVence`).** Medido: com 46 fotos geradas, *Limpar lista* deixava a tela dizendo “Adicione imagens” e a caixa com os **mesmos 17462 caracteres** — um clique separava as duas. É pré-existente do `sDel`, e o botão novo só tornou o descompasso alcançável de imediato. As **cinco** portas de mudança da lista (`sAdd`, `sDel`, `sMove`, `sListaLimpar`, `sImpAplicar`) passam a esvaziar `s-out`, porque a lista é a única parte da aba que o bloco reproduz **literalmente** — o vetor de `url` e `legenda`, na ordem —, então lista alterada é bloco que nomeia foto que não está mais lá. Onde a linha foi traçada, e por quê: **mudar configuração (intervalo, largura, proporção) não esvazia**. Isso deixa a caixa velha em silêncio, é verdade nas seis abas e não se conserta em uma só sem inventar uma inconsistência maior; está dito ao operador num `p.ajuda` embaixo da caixa. A prévia não é afetada — ela roda o gerador a cada mudança e já está certa.

**Host estranho na lista de imagens é dito, não recusado.** A fase 1 fechou o host no **importador** (`S_HOSTS_ALBOOM`, antes `S_IMP_HOSTS`), mas o cadastro manual nunca validou host: `sAdd` chama só `sUrlOk`, que confere esquema e forma. Medido, `https://evil.example/sites/4555/galleries/121894/2023...jpg?t=1` entrava **sem alerta nenhum** — e, com o corte no meio, o cartão passou a exibir apenas o nome do arquivo, **idêntico ao de uma foto legítima**, porque a pasta (onde o host mora) mede 0 px. A fase 2.5 apagou da lista o único lugar onde o host era legível. A correção **não** é recusar: o campo aceita URL completa e o operador pode ter motivo legítimo para hospedar uma foto fora do storage. São duas peças: `sAdd` **avisa** com `confirm` quando o host não é esperado (dá para seguir em frente), e `sRender` marca o host **só nessas linhas**, num selo vermelho (`.url.partida .host`, `flex-shrink:0`, teto de 12em). O efeito é o inverso do que havia: as 46 linhas normais seguem limpas e a estranha salta aos olhos, em vez de se disfarçar. `sHostEsperado` trata caminho a partir da raiz como esperado (é o próprio site) e compara a autoridade inteira por igualdade exata, a mesma lista da trava do importador — uma lista só, para não existir host travado num lugar e comum no outro.

**Acentos no texto de interface: uma convenção só.** O `index.html` é UTF-8 e declara `<meta charset="UTF-8">`; o texto que a **ferramenta** mostra ao operador vai com o **caractere literal**, acento e travessão inclusive. Não é gosto: é o que o bloco de script já fazia em 142 das 147 letras acentuadas e em 13 dos 16 travessões. O motivo de estar escrito é prático — com as duas convenções convivendo, quem procura por `configuração` acha metade das ocorrências, porque as outras estão escritas com a letra acentuada em escape (`configura` + `\u00e7` + `\u00e3` + `o`) e nenhuma busca de texto as alcança. O escape `\uXXXX` fica reservado a três casos: faixa de caracteres em expressão regular; sinal que se confunde a olho no código-fonte (`•`, `·`, `€`, aspas curvas, setas, `✕`); e string concatenada **dentro do código gerado**, onde o fonte da ferramenta se mantém ASCII (hoje só o desenho do botão PayPal em `mockPP`). Vale lembrar que isso é sobre o código da **ferramenta**: o código **gerado** continua sem acento nenhum, pela regra do Manual do Prosite (§3).

**Prévia: rodar o gerador, não imitá-lo.** Prévia que redesenha o resultado com código próprio é uma segunda implementação do gerador, e duas implementações divergem — na aba Contagem regressiva divergiram duas vezes antes de a duplicação ser removida (escape de HTML presente num lado e ausente no outro; urgência sem ramo de saída no código gerado, com o ramo correto na prévia). O padrão para abas com prévia dinâmica é: a função que monta o bloco entregue (`cBloco` na contagem regressiva) é **fonte única**, e a prévia executa o retorno dela dentro de um `<iframe>` de mesma origem, montado por `document.write`. Ganha-se fidelidade por construção — não por esforço de cópia. Três cuidados que vêm junto:

- **Storage falso.** Se o bloco gerado grava em `localStorage`/`sessionStorage`, injetar no iframe, *antes* do bloco, um shim que troque os dois por objetos em memória. Sem isso a prévia suja as chaves reais da origem da ferramenta e, na segunda abertura, nasce com a contagem já gasta. O bloco entregue continua idêntico: o shim é do ambiente da prévia.
- **Enchimento e alternador de largura.** Blocos cinzentos abaixo da barra dão altura para rolar (sem eles não dá para ver `padding-top`, entrada "depois de rolar" nem barra fixa); dois botões trocam a largura lógica do iframe para atravessar o corte de `@media` configurado, e quem avalia a media query passa a ser o próprio iframe. **Campo numérico que entra numa media query precisa ser preso à faixa declarada na própria `cCfg`, não só na largura da prévia**: `min`/`max` de `<input type="number">` não são impostos a valor digitado, e prender apenas a largura da prévia faz o iframe ir para um valor e o CSS gerado ficar em outro — a media query não casa e o modo Celular exibe layout de computador sem avisar. Preso na fonte da configuração, os dois lados leem o mesmo número. Mas clamp sozinho corrige o código entregue **em silêncio** — o operador lê 100 na tela e copia `max-width:320px`, o mesmo defeito invisível que esta aba já recusou duas vezes no limiar de urgência. Então o campo também **se corrige na interface**, no `change`/`blur`: o valor preso volta para o input, a correção acontece à vista, e o clamp da `cCfg` fica como rede para estado restaurado do `localStorage`. Nunca no `input` — corrigir a cada tecla impediria digitar "320", porque o "3" viraria 320 antes do resto chegar.
- **Falha do shim tem que ser barulhenta.** O `try/catch` do bloco gerado não denuncia um shim que não instalou: `setItem` no Storage real funciona e não lança, e o sintoma só apareceria na segunda abertura da aba como contagem vencida. O shim marca o objeto em memória (`fcPvMemoria`), confere depois da troca e, se não instalou, insere um aviso vermelho visível no topo da prévia.
- **Debounce com timer único.** Remontar a cada tecla pisca e custa caro: 400 ms para mudanças de campo, imediato no botão "Atualizar prévia". Cancelar o timer anterior antes de agendar outro.

O `<p class="ajuda">` abaixo da prévia continua obrigatório, mas muda de conteúdo: em vez de listar o que a prévia não mostra, declara o que ainda difere da página publicada (na contagem regressiva: a barra fixa gruda no topo do quadro e não da janela, o relógio é o da máquina do operador, e a contagem sempre começa agora em vez de na primeira visita do visitante).

O bloco `prefers-reduced-motion` sai sempre que houver movimento — por `animation` ou por `transition` — e cobre barra, conteúdo, dígitos e barra de progresso. O radio "fixa no topo / no fluxo" decide o destino: Tag Body ou componente HTML — nunca a Tag Head, porque o bloco é autocontido. Decisões da revisão final (ago/2026): a urgência troca `backgroundColor` (nunca o shorthand `background`, que apagaria brilho e degradê) e tem ramo de saída, para o modo "reiniciar o ciclo" voltar ao normal; os dois intervalos (tique e alternância) são derrubados juntos no fim e no clique de fechar; o `padding-top` da barra fixa acompanha a classe `fcb-visivel`, não a montagem; o trilho da rolagem repete o conteúdo até cada metade cobrir o container (o `translateX(-50%)` exige duas metades idênticas); e `cGerar` recusa código de campanha vazio, nenhuma unidade marcada, limiar de urgência maior ou igual à duração total e `href` de CTA com esquema fora de âncora/caminho relativo/`http(s)`. **Prévia fiel (ago/2026):** a prévia deixou de ter motor próprio — `cFormatarHTML`, `cPartes`, `cAlvoMs` e `cDois` foram removidos, e `cGerar` foi partido em validações + `cBloco(cfg)`, que devolve o bloco. `cPvMontar` escreve, num iframe de mesma origem dentro de `#c-pv-box`, o shim de storage → o retorno de `cBloco` → o enchimento cinzento; o alternador Computador/Celular troca a largura lógica do iframe (`Math.max(920, mob+240)` contra `Math.min(380, mob)`, sempre atravessando o corte configurado), reduzida por `transform:scale` do lado de fora para caber na coluna sem mexer na viewport que a media query lê. `cCfg` passou a prender `mob` a `[320,1024]` (a faixa declarada no campo — desde a revisão final de ago/2026 a faixa vem de `C_NUMS`, junto com os outros treze campos numéricos da aba) — valor dentro da faixa passa intacto e a saída gerada não muda; valor fora dela era emitido inteiro no `@media` e fazia o modo Celular mentir. A prévia é montada **só no clique da aba**, nunca no carregamento da ferramenta: montar na carga executaria o bloco (intervalo de 1 s, listeners, `ResizeObserver`) para quem nunca abre a aba, e ainda com o painel escondido.

7. **Link de cobrança** (ago/2026) — para serviço já combinado: uma **página fixa** publicada uma vez (componente HTML em, por exemplo, `/pagar`) e um **link diferente por cobrança**. A página mostra descrição, valor, Pix (copia e cola + QR Code), PayPal (botão do SDK ou link de cobrança criado no próprio PayPal, escolha **por cobrança**) e o botão “Já paguei” pelo WhatsApp. **O valor exibido e o valor cobrado saem os dois do campo 54 do código Pix que viaja no link** — nunca de um parâmetro à parte. Duas saídas com vidas diferentes: o **bloco** (uma vez) e o **link** (a cada cobrança). Detalhes logo abaixo.

> Histórico: até ago/2026 existiam abas separadas de Checkout PayPal e Checkout Pix; foram unificadas na aba Checkout, que passou a ter seletor de formas de pagamento e múltiplos produtos. Nada se perdeu — o modo "somente PayPal" preserva a escolha de moeda, e o "somente Pix", o carrinho sem PayPal.



### Link de cobrança (ago/2026, a sétima aba) — uma fonte de valor, não duas

**O problema e o limite.** Serviço combinado, falta receber. Não há servidor neste projeto, então qualquer conferência roda no computador do cliente e pode ser desligada por ele: o objetivo **não é impedir** a alteração, é fazer com que alterar **não adiante**. Pix e PayPal se comportam de maneira oposta nisso — no Pix o valor mora dentro do próprio código que o aplicativo do banco lê e o banco trava nele; no botão do PayPal o valor é calculado no navegador e é adulterável. Daí sai a regra da aba inteira: **o valor exibido e o valor cobrado saem os dois de dentro do código Pix que viaja no link**. Uma fonte, não duas que podem divergir — o mesmo princípio que rege as prévias.

**As três conferências da página publicada, nessa ordem, e por que são três.**

1. **Forma e CRC** (`pixLer`). Diagnóstico barato para o caso comum: link truncado, dígito trocado, ou campo cujo comprimento declarado não bate com o conteúdo. Medido na página publicada do Prosite: um campo 54 declarando comprimento `07` para o valor `75.00` faz um leitor por posição devolver **`75.0058`** — sete caracteres, invadindo o campo seguinte, valor errado sem erro nenhum. Por isso `lerTlv` percorre campo a campo e **exige que a estrutura feche exatamente no fim**: comprimento que não seja dois dígitos, valor mais curto que o declarado ou sobra de bytes derrubam a leitura inteira. Provado nos dois sentidos (comprimento declarado maior e menor que o real, ambos com CRC recalculado): as duas são recusadas.
2. **Campo 54 presente e bem formado.** Pix sem valor deixaria o pagador digitar o que quisesse, que é o que esta aba existe para impedir. A recusa acontece **também na geração**: `pGerarLink` monta o payload e o relê pela *mesma* `pixLer` antes de escrever o link — nenhum link sai daqui sem valor, ou com valor diferente do digitado.
3. **Remontagem.** A página remonta o payload a partir dos **seus próprios** dados de recebedor (chave, nome, cidade) mais o valor e o txid lidos, e exige igualdade byte a byte com o código recebido. Quem recalcula o CRC passa na conferência 1; sem a chave desta página, não passa nesta. De quebra, ela recusa link montado com a chave Pix de **outra pessoa** — ninguém usa a página de pagamento do dono para receber na conta dele.

**O limite, medido e dito sem exagero — na interface e no comentário do código.** A chave Pix é pública por definição, então quem souber recalcular o CRC monta um payload legítimo *do próprio dono* com valor **menor**, e as três conferências passam: medido, `1200.50` trocado para `1200.90` com o CRC refeito é exibido normalmente. Isso não é furo do desenho, é o que ele promete: a página garante que **tela, Pix e PayPal digam o mesmo número**, nunca que o número seja o que o dono queria. Dá para *tentar pagar menos*; não dá para *enganar sobre quanto se pagou*. Impedir exigiria um segredo que o cliente não lesse — ou seja, um servidor. Premissa operacional registrada: **o dono confere o valor recebido antes de entregar o trabalho**.

**A descrição é cosmética** e viaja em parâmetro próprio: alterá-la não muda um centavo. Ela também **nunca entra no código-fonte do bloco** — chega em tempo de execução e vai para `textContent` —, então texto hostil na descrição não tem por onde quebrar o bloco publicado. Medido com `'`, com a sequência de fechamento de script e com abre-comentário: o texto sai literal, nenhum script executa e o conteúdo depois do bloco sobrevive. Os **textos do cartão**, esses sim, entram no código-fonte e passam por `escJs`; medidos com o mesmo material hostil, com o mesmo resultado.

**Reúso: unificou-se a fonte que escreve, nunca a saída.** A aba Checkout já escrevia `tlv`, `crc16`, `semAcento` e a montagem do BR Code **dentro do bloco gerado**. Com a sétima aba o mesmo payload passaria a ser preciso em três lugares (o carrinho, a página de cobrança e a **própria ferramenta**, que monta o código na hora de gerar o link) — três cópias do mesmo TLV e do mesmo CRC, e aqui divergir não é cosmético: é o banco recusar o QR sem explicação, ou cobrar outro valor. A maquinaria virou `FC_PIX_SRC`, no bloco de utilidades, e ganhou duas peças novas (`lerTlv`, `pixLer`). O lado da ferramenta **não reescreve as funções**: `fcPixApi()` **avalia a mesma fonte** (`new Function` sobre texto literal do arquivo, sem nada digitado pelo operador), então o código que a ferramenta executa é, caractere por caractere, o que o bloco publicado vai executar. Prova de que nada mudou para o Checkout: as **9 saídas** dos seis geradores continuam byte a byte idênticas às de `main`, em três cenários — inclusive um com PayPal e Pix no mesmo bloco.

Junto vieram outras quatro unificações, todas pelo mesmo motivo (a cópia seria a de número dois ou três): a **formatação de preço** (`PRECO_MOEDAS`, `precoFmt`, `fcMoedaFmtGer`) subiu da aba Checkout para as utilidades — o sinalizador `soReal` existe porque na página de cobrança o pedido é sempre em real e as duas linhas de outras moedas seriam código morto; a **limpeza e os limites da chave Pix** (`pixLimpar`, `pixChaveErro`, `fcPixChaveAjustar`, que passou a receber o id do campo) subiram pelo mesmo caminho, porque duas abas agora têm campo de chave; a **coruja** (`CORUJA_PECAS`/`corujaJs`) e as **cores** (`corSegura`/`CORES_LIVRES`) já eram compartilhadas e foram consumidas como estão; e a **faixa numérica** entrou como `P_NUMS`, no formato das outras seis.

**O shim das prévias virou um só (`fcPvShim`).** Ele estava copiado quatro vezes — Slideshow, Leads, Checkout e Contagem —, e a quinta cópia seria a desta aba. O que muda por aba entra por parâmetro (`pref`, `abre`/`fecha` do texto do aviso, `extras`, `conferencias`, `depois`, que é onde a sonda do botão PayPal do Checkout continua). Prova de que a unificação não mudou uma vírgula: o texto do `<script>` do shim dentro do iframe das quatro prévias é **idêntico** ao de `main`.

**A prévia executa o bloco, e a novidade é o endereço.** O bloco lê `location.search`, e um quadro escrito por `document.write` não tem parâmetros. Um iframe **sem `src`** herda o endereço do documento de cima, e `history.replaceState` escreve ali a consulta desta cobrança — o bloco entregue continua lendo `location.search` normalmente, byte a byte igual ao da textarea. Vale a obrigação de sempre: a troca é **conferida** (`location.search` tem de ser exatamente o que se pediu) e, se não pegar — num `file://` o `replaceState` lança `SecurityError` —, um aviso vermelho entra no topo do quadro. Provado forçando a falha: o aviso nomeia o armazenamento, o endereço simulado e o SDK do PayPal. Os **três estados** são botões: cobrança válida, código adulterado (um dígito trocado) e link sem parâmetros. O SDK do PayPal **não roda na prévia** — o shim o intercepta e desenha o botão, exercitando o `createOrder` do próprio bloco para exibir *o valor que iria na ordem*: é assim que se prova, medido e não presumido, que o valor do PayPal é o mesmo da tela.

**Mudou a cobrança, a caixa do link esvazia (`pSaidaVence`).** Mesmo critério do `sSaidaVence` do Slideshow — a caixa esvazia quando o que mudou é reproduzido **literalmente** na saída. O link reproduz descrição, valor e identificador, e o payload dentro dele reproduz chave, nome e cidade: trocar qualquer um deles e deixar o link antigo na caixa seria copiar, sem nada na tela indicando isso, um link com o valor da cobrança **anterior**. Aparência e textos do cartão **não** esvaziam nada: eles mudam o bloco, e ali quem avisa é o painel consolidado.

**A integração exigiu duas mudanças na maquinaria compartilhada, e nenhuma delas é um caso especial da aba nova.**

- **`trocarAba` deixou de ter a lista das abas cravada** e passou a derivá-la de `ABAS` (`fcAbasIds`). Com a lista repetida, a sétima aba nasceria com o painel nunca escondido nem marcado como ativo — lista fechada de seis é exatamente onde a sétima quebra em silêncio.
- **`naoEmite`, o caso simétrico de `fora`, em `fccAssinar`.** `fora` é o campo que **não** viaja no preset mas **muda** o que a aba emite (`b.consol`). `naoEmite` é o oposto: campo que viaja no preset e **não** muda o que a aba emite — aqui, a descrição, o valor, o identificador e o modo de PayPal, que vão para o **link** e nunca para o bloco. Sem essa linha, digitar a descrição de uma cobrança nova faria o painel anunciar que o bloco da página está velho, sobre um bloco que não mudou nem podia mudar. Medido: trocar descrição e valor **não** dispara o aviso; trocar o título do cartão **dispara**.

**O número de abas saiu das frases.** A palavra "seis" estava escrita em catorze mensagens que o operador lê — inclusive na que ele lê ao criar um preset geral (*"as seis abas nasceram FORA desta página"*) e na que descreve o que o backup leva. Com a sétima, todas passariam a mentir por um. Agora o número vem de `ABAS.length`, por extenso (`fcAbasTxt`), e o que sobrou escrito é citação histórica.

**O que o painel consolidado faz com ela.** Só o **bloco** (`p-out1`) entra, na lista de saídas por componente. O **link** não vai para campo nenhum do Prosite — vai para o cliente —, então o painel, que existe para montar os campos da página, não teria onde encaixá-lo; listar as duas saídas juntas confundiria as duas vidas que a aba acabou de separar. A nota ao lado do item diz isso.

**Backup.** Os `operacionais` da aba são cinco: chave Pix, nome e cidade do recebedor, Client ID do PayPal e WhatsApp do comprovante. Medido: a pergunta de exportar os cita, o arquivo *com dados* os traz, o arquivo *sem dados* os omite — tanto no rascunho quanto dentro do preset geral — e a ida-e-volta devolve o fragmento `p` idêntico.

**Espaço de nomes do código gerado: `fcpg-`**, e não `fcp-`. `fcp-` é o prefixo da **biblioteca de presets** dentro da ferramenta; usar o mesmo no bloco entregue misturaria as duas coisas num grep só, que é o motivo pelo qual a fase 4 escolheu `fcx-` em vez de `fcb-`.

**Limites registrados, para não serem descobertos na página publicada.** O link vai sempre **individualmente**: em grupo, descrição e valor aparecem na pré-visualização de link para todo mundo na conversa. Trocar a chave Pix e regerar o bloco **invalida os links ainda não pagos** — é o comportamento certo (um link que não pertence mais àquela página não deveria abrir), mas custa gerar links novos. E o Pix estático não confirma pagamento sozinho: ninguém avisa a página quando o dinheiro cai.

## 5. Decisões de arquitetura registradas

- **Sem servidor, sem segredos**: tudo roda client-side. Client ID do PayPal e chave Pix são públicos por definição; Secret do PayPal nunca é usado.
- **Stripe**: descartado como checkout próprio (valor dinâmico exige chave secreta em servidor). Permanece só como processador interno do TidyCal.
- **Boleto PayPal**: descartado (exige webhook/servidor; assíncrono não combina com reserva).
- **Pix pelo PayPal (PPCP)**: existe desde abr/2026 mediante solicitação/elegibilidade, formato link de valor fixo — não integrado; nosso Pix estático cobre melhor.
- **Parcelamento PayPal**: ativa-se no painel (até 12x, recebimento à vista); confirmado funcionando inclusive no botão preto (guest).
- **Pix estático não tem confirmação automática** → conciliação por extrato + mensagem do WhatsApp ("Já paguei").
- Efeito pulsar em **texto do editor** Prosite: abandonado (ver manual, item 9). Já em **componentes**, animações funcionam: o caminho validado é `@keyframes` no head + `animation:` nas propriedades do campo CSS Customizado (base da aba "Bordas com efeito").
- **Importador de galeria da aba Slideshow** (ago/2026). Cadastrar foto a foto era proibitivo — as duas galerias medidas têm 46 e 58 fotos —, e foi por isso que a aba Slideshow ficou vazia depois da fase 5. Cinco medições sustentam o desenho, e cada uma descarta uma alternativa mais simples:
    - **Origem cruzada impede ler a página sozinho.** De `http://localhost:8977` contra `https://www.fotocerta.com.br/…`: `TypeError: Failed to fetch`. Não é defeito, é política do navegador, e só um servidor contornaria — que este projeto não tem por decisão. Daí as **duas colagens**: o link (de onde sai o número da galeria) e o código-fonte (de onde saem os endereços). Os dois juntos são o que permite **recusar com explicação** quando o operador cola a fonte de uma galeria com o link de outra — o erro mais provável do fluxo, porque as duas colagens vêm de janelas diferentes.
    - **A fonte tem mais fotos que a tela.** Na *Estúdio Temático*, 10 fotos carregadas no navegador contra 46 na fonte (o resto entra ao rolar). Colar a fonte não é só o jeito possível: é o que não perde foto.
    - **Cada foto aparece várias vezes, embrulhada num redimensionador.** 139 endereços para 46 fotos. O desembrulho é **tudo depois de `/url/`, prefixado com `https://`** — deliberadamente agnóstico ao verbo (`crop`, `resize` e `resize/…/scale/2` convivem na mesma página; casar os verbos quebraria no dia em que a Alboom acrescentasse o terceiro). A junção das repetidas acontece **depois** de desembrulhar, com chave sem a parte de consulta (o mesmo arquivo aparece com `?t=` diferente entre recortes) e guardando o endereço da primeira aparição, com o `?t=` preservado.
    - **A ordem é a da grade da página, e por isso é a da *última* aparição** (rodada de correção). A foto de **capa** aparece antes da grade — no `<meta itemprop="image">` da galeria, no `<picture>` do topo do portfólio —, e guardar a posição da primeira aparição a fazia pular da posição 22 (galeria) ou 34 (portfólio) para o começo: conjunto certo, ordem que o operador não reconhece. Medido nos dois códigos-fonte: cada foto aparece **2** vezes e a capa **3**, e a única aparição anterior à grade é a extra da capa (1 de 93 e 1 de 117); dentro da grade, as duas aparições da mesma foto são vizinhas (`data-retina` e `data-original` do mesmo item). Ordenar pela última aparição devolve a ordem da grade — conferido item a item contra a marcação do tema (`cgc__item`, `acg__item`): **46 de 46 e 58 de 58, idênticas**. O **endereço** guardado continua sendo o da primeira aparição, e isso não muda nada: medido, o endereço completo não varia entre as aparições da mesma foto (0 de 46 e 0 de 58), então a correção mexe só na posição. Limite honesto: uma repetição emitida *depois* da grade jogaria aquela foto para o fim — mesmo defeito na direção contrária.
    - **O filtro é a pasta da galeria, derivada do número do link** (`/gallery/121894-…` → `/galleries/121894/`; `/portfolio/ensaio-casal/1518588-…` → `/albuns/1518588/`). O número do site (`4555`) **não** entra no critério: casar só por `/galleries/<número>/` mantém o importador vivo se a Foto Certa publicar de outro site da Alboom. O filtro por pasta é o que exclui logotipo, imagens do tema e as miniaturas de "galerias relacionadas" do rodapé — conferido contra a marcação: 46 endereços para 46 `cgc__item`, 58 para 58 `acg__item`.
    - **A pasta diz de que galeria, não de que servidor: por isso há lista de permissão de host** (rodada de correção). O host é tudo que vem logo depois de `/url/`, e quem escreveu a página colada escolhe esse texto. Medido, entrando na lista antes da trava: `/url/evil.example/galleries/121894/a.jpg` aceito; `/url/storage.alboom.ninja@evil.example/…` aceito **e exibido começando por `storage.alboom.ninja`**, passando por legítimo para quem confere 46 linhas; `/url/127.0.0.1:8979/…` aceito; `evil&#46;example` (entidade) aceito. Esses endereços iriam para dentro do bloco publicado no site do cliente — explorar exige texto hostil na página colada, então é defesa em profundidade, mas nada conferia host. A regra é **igualdade exata da autoridade inteira** (tudo entre `https://` e a primeira `/`, `?` ou `#`) contra `storage.alboom.ninja` e `alfred.alboompro.com`: é a autoridade inteira que recusa `usuario@host`, porta e host vazio, e comparar por sufixo aceitaria `evil-alboom.ninja`. `sUrlOk` **não serve** para isso — ela é agnóstica a host de propósito, porque o cadastro manual aceita foto de qualquer lugar. O mesmo filtro roda no diagnóstico do caso zero, senão ele nomearia galerias que o importador jamais aceitaria.
    - **Nome de arquivo cortado é descartado contando** (rodada de correção). A classe de caracteres da extração para em `'`, `<`, `>`, `)` ou espaço; um nome com um desses sairia truncado (`…/galleries/121894/it`), e o toco continua sendo um `https` válido — passava por `sUrlOk` e entrava na lista como foto que dá 404 na página publicada, sem ser contada em lugar nenhum. Latente hoje (a Alboom normaliza nomes), mas é a falha muda que este projeto recusa. Medidas as 104 fotos, **todas** terminam em `.jpg` e trazem `?t=`, então exigir extensão de imagem no fim do caminho detecta o corte sem recusar nada legítimo. As três recusas (host, corte, endereço inválido) contam **endereços distintos, nunca aparições** — contar aparições anunciaria "117 descartadas" numa página de 58 fotos.
    - **A mesma validação roda na conferência e na aplicação.** Antes, `sUrlOk` só rodava na aplicação: medido, a conferência dizia "Encontrei 1 foto" e a aplicação somava 0 — dois números discordando na mesma tela. Agora a conferência valida os **dois** endereços finais possíveis (o de 1200 px e o embrulhado de 900 px), porque o tamanho só é escolhido depois; a rede que continua em `sImpAplicar` deixa de ter como recusar algo que a conferência contou.
    - **Legenda: o título serve, a descrição não.** Todas as fotos compartilham o mesmo texto de descrição, escrito para buscadores. O importador extrai o título e o oferece preenchido como sugestão — o `<h1>` antes do `<title>`, porque no portfólio medido o `<h1>` é "Fernanda & Ricardo {Pré.Casamento}" enquanto o `<title>` emenda ensaio, local, cidade e estado.
    - **O "1400 px" do plano não existe: seria upscale.** Medidas as 104 fotos das duas galerias, o storage **já entrega tudo com 1200 px de largura** (85 fotos 1200×~800, 19 retratos 1200×~1800), **de 157 a 868 KB por foto**, mediana 340 KB — a faixa "150 a 610 KB" registrada na primeira versão estava errada (seis das 104 passam de 610 KB), e a conclusão sobrevive à correção, o número não. Pedir 1400 px ao redimensionador responde 200 e devolve uma imagem de verdade — 1400×933 —, mas esticada a partir do original de 1200×800, e em 3 das 5 fotos medidas o arquivo saiu **maior** que o original. A premissa do plano ("originais de vários megabytes") estava errada. As opções entregues são o que a galeria entrega (1200 px) e uma redução real para **900 px**, a largura padrão do slideshow (15% a 55% menos bytes por foto). Medido também que o `?t=` do original **não** atrapalha ao ser embrulhado: o redimensionador devolveu byte a byte o mesmo arquivo com e sem ele.
    - **Conferência em dois passos, não um botão só.** "Conferir a galeria" descobre e informa (quantas fotos, de qual galeria, qual título, quantas **já estão** na lista, quantas são novas e qual o total resultante); só então "Adicionar N fotos à lista" mexe na lista, e o próprio rótulo do botão traz o número. Aplicar zera o resultado, senão um segundo clique duplicaria a galeria inteira em silêncio; mudar o link ou a fonte depois de conferir invalida o resultado e diz por quê, senão entrariam as fotos da galeria anterior sem nada na tela indicando isso.
    - **A sobreposição com a lista é medida, não prometida** (rodada de correção). A versão anterior dizia quantas a lista **tem**, nunca quantas dela **já estão** nela: reimportar a mesma galeria anunciava só "ficando 92 no total" e entregava 46 duplicadas. A comparação é por **endereço desembrulhado sem a parte de consulta** — o mesmo arquivo pode já estar lá em outro tamanho, e comparar o endereço cru diria "nenhuma repetida" com a foto entrando duas vezes. Reportar, e não decidir: as repetidas **entram** (repetir foto num slideshow pode ser proposital), mas a conferência diz quantas são e a aplicação repete o aviso. A contagem é refeita nos dois momentos, e não guardada, porque remover uma foto da lista não invalida a conferência.
    - **A sugestão de legenda se atualiza entre galerias sem sobrescrever o que foi digitado** (rodada de correção). Não havia como distinguir "o operador digitou" de "preenchemos automaticamente da última vez": medido, importar a galeria punha "Estúdio Temático" no campo e, ao conferir o portfólio, a mensagem anunciava *"Fernanda & Ricardo"* enquanto o campo ainda dizia "Estúdio Temático" — as 58 fotos recebendo a legenda errada, com a contradição a uma linha de distância. A marca é o **próprio texto que escrevemos** (`sImpLegAuto`), não um booleano: sobrescreve se o campo estiver vazio ou contiver exatamente aquilo, e nunca em qualquer outro caso.
    - **Nada do que se cola ali é salvo.** O código-fonte chega a centenas de milhares de caracteres e não pode disputar espaço com a configuração das seis abas em `fcConstrutores` — conferido: 98 KB colados, 3,4 KB gravados, chaves inalteradas. Pela mesma razão, nenhum campo `s-imp-*` alimenta a prévia (remontar o iframe a cada tecla do campo do código-fonte mandaria o navegador rebaixar todas as fotos sem nada mudar na tela).
    - **O importador só acrescenta um caminho de entrada.** Ele alimenta a mesma lista `sImgs` e não toca em `sCfg`, `sBloco` nem `sGerar`. Verificado por regressão: com a lista preenchida à mão, a saída `s-out` é byte a byte idêntica à de `main` (8478 e 6729 bytes, com e sem os recursos da fase 5 ligados).
- **Bordas com efeito** (origem: landing de Natal 2026, blocos "Presenteie uma família" e card "Pack Standard"): brilho = **contraste alto** entre base escura e facho claro, com facho **estreito** (~5% do ciclo) — cores próximas em luminosidade viram ondulação sutil. Cor renderizada muda com o contexto: validar sempre na página real, não no mockup. O Prosite não permite selo/badge flutuante sobre card — a borda animada cumpre esse papel (com o texto "O mais escolhido" na primeira linha).

- **Campo do operador se corrige na interface, nunca em silêncio no gerador** (regra nascida no `c-mob` da Contagem e estendida em ago/2026 às cores das abas Leads e Checkout e, na fase 3, a **todos os campos numéricos das quatro abas restantes**: `B_NUMS` na Bordas, `T_NUMS` no TidyCal, `S_NUMS` no Slideshow e `L_NUMS` na Captação de leads. Cada aba declara só a tabela de linhas `[id, padrão, min, max, inteiro]`; a mecânica é uma só, no bloco compartilhado (`fcPreso`, `fcAjustar`, `fcAjustarTodos`, `fcLigarFaixa`) — a mesma linha alimenta o gerador e a interface, então não há como a saída ser presa numa faixa e a tela mostrar outra. A correção roda no `change`/`blur`, nunca no `input`, e também **na carga**, para estado gravado antes da regra não exibir um número diferente do que o gerador vai usar. **Corrigido na revisão final (ago/2026): a Contagem regressiva não ficava de fora — ficava de fora indevidamente.** A justificativa registrada aqui ("o `c-mob` dela é campo único") era falsa: a aba tem **catorze** campos numéricos, e só dois deles (`c-mob` e o teto da coruja) tinham faixa. Os outros doze passavam por um `cNum` que trocava `NaN` pelo padrão e nada mais. Medido, tudo sem aviso e com o campo continuando a exibir o valor digitado: `c-largmax=0` gerava `max-width:0px` (barra de largura zero); `c-tam=0` gerava `font-size:0px`; `c-vel=0` gerava `animation:fcb-rola 0s` (a rolagem escolhida nunca acontece); `c-urglim=-5` fazia a urgência nunca disparar. Agora os catorze estão em `C_NUMS`, `cNum` e `cMobAjustar` foram removidos, e `cCfg` lê tudo por `cPreso` — uma linha por campo alimentando a tela e o gerador. Uma afirmação falsa numa justificativa de exclusão mantém a lacuna aberta por três fases: quem lia a documentação achava que a aba já estava coberta. Casos que isto fechou: `s-int` 100 saía como `INTERVALO = 100` enquanto a prévia rodava a 1500 — a `sPreview` tinha um `Math.max(1500, …)` próprio, segunda implementação do mesmo limite, e passou a ler a tabela; `l-segauto` 0 caía no `||` e virava 8 em silêncio; `l-segef` −5 saía inteiro e fazia `setInterval` disparar sem parar): valor inválido é substituído pelo padrão **no próprio campo**, no `change`/`blur` (nunca no `input`, que impediria digitar), com o seletor de cor acompanhando. Assim tela e código mostram sempre o mesmo valor. O gerador mantém a validação como rede (`corSegura`), que é quem segura estado restaurado do `localStorage` gravado antes da regra. Antes disso, a prévia validava a cor e o gerador não: o operador via verde-escuro e publicava `naoehcor` — ou, com um apóstrofo no campo, um bloco que executava código arbitrário no carrinho.
- **Link de cobrança sem servidor: detectar onde impedir é impossível** (ago/2026, sétima aba). O valor viaja **dentro** do código Pix e a página o lê de lá para a tela e para o PayPal, então os três não têm como divergir; forma, CRC e remontagem com os dados do recebedor recusam link mexido e link de terceiro. O que **não** é possível sem servidor, e está dito na interface: quem recalcula a verificação interna monta um link do próprio dono com valor menor, e a página exibe esse valor — o banco cobra o mesmo número. A garantia é de coerência, não de valor. A conferência do extrato antes da entrega é o que fecha o desenho. Ver §4.
- **Chave Pix (aba Checkout)**: nome e cidade já passavam por `semAcento`; a chave ia crua. Regra adotada, **por posição e não por tipo de caractere**: nas **pontas**, espaço e invisível são removidos e devolvidos ao campo; **no meio**, nada é removido — espaço comum, TAB, NBSP e zero-width caem todos na mesma **recusa com aviso** (que menciona a hipótese de caractere invisível, já que o operador pode não estar vendo o problema). Também recusam: tamanho acima de 77 do padrão BR Code e campo que ficou vazio depois da limpeza. A checagem de charset vem **antes** da de tamanho — senão uma chave de 80 caracteres com emoji reportaria o tamanho quando o defeito é o emoji. Sem regra de formato por tipo de chave — o padrão aceita e-mail, telefone, CPF/CNPJ e aleatória. O limite a ASCII imprimível não é estética: `tlv()` conta com `v.length` e `crc16()` com `charCodeAt` (UTF-16), enquanto o banco conta bytes UTF-8; qualquer caractere fora da faixa faz comprimento e CRC discordarem e o banco recusa o QR sem explicação.

- **A configuração sai do navegador em arquivo, e o arquivo que volta é entrada não confiável** (ago/2026, fase 4). Tudo o que a ferramenta guarda vive no `localStorage` de um navegador — some ao limpar os dados do site e não acompanha outro computador —, e o `.json` de backup é a única saída. A decisão que manda no desenho é a do sentido inverso: um JSON importado vira configuração, e a configuração vira **código publicado no site do cliente**, então ele é tratado como a fase 1 tratou o código-fonte colado. Três camadas na entrada (forma → regra da aba → travas que já existem), nenhum caminho novo de escrita de campo, e nada descartado em silêncio. Duas descobertas da verificação como operador ficaram registradas: a **data do arquivo é ecoada na confirmação** e, sendo texto livre, podia trazer uma frase que mentia sobre o que a confirmação estava prestes a fazer (hoje só forma ISO passa); e **uma mensagem não pode dizer as duas coisas** — a linha do "caiu no Rascunho" inserida entre "o rascunho foi aplicado" e o `senão` "NÃO foi aplicado" fez a mesma mensagem afirmar as duas. Detalhes em §4.
- **Arquivo único, abas isoladas** (ago/2026): separar o `index.html` em vários arquivos foi avaliado e **recusado** — desempenho irrelevante (24 ms de carga) e até negativo (+5,8% comprimido, porque o gzip perde o dicionário compartilhado), módulos ES matariam o "abrir do disco e testar" documentado, e scripts clássicos separados criariam um modo de falha novo (um `.js` esquecido no `git add` publica uma aba morta e silenciosa). Em vez disso, o isolamento veio por desenho: `try/catch` por aba no salvamento, na restauração e na partida, mais as funções compartilhadas no topo. Se um dia a discussão voltar (sétima aba, ou uma aba passando de ~1.200 linhas próprias), a forma recomendada é **um `<script>` por aba dentro do mesmo arquivo** — entrega o mesmo isolamento sem o arquivo faltante e sem perder a portabilidade do arquivo único.
- **Movimento reduzido desliga o que a ferramenta criou, não o que o site tem** (ago/2026, fase 3). Três abas ganharam ou refizeram o bloco `prefers-reduced-motion` nesta fase; na revisão final de ago/2026 a cobertura fechou nas **seis** (TidyCal era a última sem guarda — ver a rodada de coerência mais abaixo):
  - **Bordas**: o código 1 vai para a Tag Head do **site**, e trazia `* { animation-duration: 0.01ms !important; animation-iteration-count: 1 !important; }` — matava toda animação de todas as páginas para quem tem movimento reduzido, inclusive as do tema Alboom e as dos outros blocos da ferramenta; e, no halo pulsante, congelar em uma iteração parava a animação no quadro 100%, que é `box-shadow 0 0 0 0 rgba(cor, 0)` — **halo nenhum**. A regra agora **redefine a própria animação** (`@keyframes fc-borda-*`) com um único quadro dentro do `@media`: só as animações desta ferramenta param, o efeito congela num estado legível (degradê parado; halo vira um anel estático de meio alcance na opacidade de partida) e colar vários efeitos no mesmo campo do head não gera regras concorrentes, porque cada bloco só redefine a animação que ele mesmo declarou. Efeito "borda fixa" não tem animação e passou a não gerar código 1 nenhum.
  - **Slideshow e Captação de leads** não emitiam nada. Agora emitem um bloco escopado por classe/atributo, com a **mesma especificidade** das regras de cima e depois delas no CSS (vence sem `!important`). No slideshow, a troca automática de foto **continua** — é mudança de conteúdo, não movimento na tela; parar também a passagem deixaria o visitante com uma foto só.
- **Duas galerias na mesma página (aba Slideshow)**: o bloco trazia `id="fc-slideshow"` fixo e `getElementById`, então dois componentes na mesma landing faziam os dois scripts achar a **primeira** caixa — a primeira ficava com os slides das duas e a segunda nascia vazia, sem aviso (e dois elementos com o mesmo id são HTML inválido). O id saiu: cada bloco procura a primeira `.fc-slideshow` ainda não reivindicada e a marca com `data-fc-pronto`; como os scripts rodam na ordem em que aparecem, cada um fica com a sua. Limitação que sobra e está nas instruções: o `<style>` de cada bloco redefine largura máxima e proporção para **todas** as galerias — vale o último colado.
- **"Sem halo" produzia halo (aba Bordas)**: no efeito "halo pulsante" o rádio Com/Sem halo não desligava nada — o gerador só trocava os campos por 18px/0.5 fixos e escondia os campos, então o rótulo mentia. No pulso o halo **é** o efeito: o rádio some nesse efeito (com um aviso explicando por quê e apontando "borda fixa" para quem quer moldura sem halo) e os campos de alcance e intensidade passam a valer sempre.
- **Recusar em vez de assumir, quando não há valor certo** (extensão da regra da chave Pix e do limiar de urgência): a aba **Leads** passou a recusar código da página vazio (a mensagem chegava como `(cod: **)`, defeituosa e muda); o **TidyCal** recusa endereço da intermediária vazio ou com esquema fora de `http(s)`/caminho relativo (`src=""` gerava um iframe que não carregava nada; `javascript:` era aceito); e o **Checkout** recusa cupom com valor zerado ou apagado **na lista** (o formulário de cadastro validava, o editor da lista não) e cupom em porcentagem acima de 100%, que zera o pedido. O carrinho gerado ganhou, no PayPal, a guarda de total zero que só o Pix tinha — via `onClick`/`actions.reject()`, com mensagem própria em vez do erro genérico.
- **Prévia x gerado no modo "vários produtos" (Checkout)**: divergiam — a prévia abria com o primeiro produto marcado e total preenchido, o carrinho publicado abria com nada marcado e R$ 0,00. Quem mudou foi o **gerado**: carrinho que abre zerado não é só infidelidade da prévia, é o estado inicial que levava total zero ao PayPal. O `if(tipoProd==='radio'&&i===0)` virou `if(i===0)`, e a legenda da prévia passou ao formato novo (declara o que ainda difere da página publicada em vez de descrever o que a prévia faz).
- **Editores em linha também se corrigem à vista** (rodada 3): o código do cupom era gravado em maiúsculas no modelo mas não devolvido ao campo (tela `promo abc`, código `PROMO ABC`), e o preço de opcional apagado virava `preco:0.00` com o campo em branco. Os dois passaram a se corrigir no `change`/`blur`. A diferença de tratamento entre eles é deliberada: **cupom** de valor zero é **recusado** (não há leitura legítima — promete desconto e entrega "Desconto − R$ 0,00"), enquanto **opcional** de preço zero é **aceito com o campo assumindo o `0`** (opcional grátis é configuração legítima; a própria aba já emite `Sem opcional` a preço zero). Resíduo registrado e não tratado: o **nome** do opcional também pode ser esvaziado pelo editor em linha, e sai como `{nome:''}`.
- **`tUrlOk` (TidyCal) recusa endereço protocol-relative**: `//evil.com/x` começa com barra mas resolve para **outro host**, herdando só o esquema da página — o teste passou a exigir uma barra só.
- **O aviso "Copiado!" precisa dizer a verdade** (helper compartilhado, ago/2026): `copiar()` engolia a falha do `execCommand` num `catch` vazio, chamava `navigator.clipboard.writeText` sem conferir o resultado (é assíncrono) e mostrava o aviso **antes** de qualquer um dos dois responder — então dizia "Copiado!" acontecesse o que acontecesse, nas seis abas. O caso realista não precisa de má-fé: a ferramenta aberta por um endereço `http` de rede local (ou por `file://`) não está em contexto seguro, `navigator.clipboard` nem existe e o `execCommand` é recusado; o operador colava conteúdo velho no Prosite achando que tinha copiado o novo. Agora o aviso espera a resposta e tem dois estados — verde "Copiado!" (caminho de sucesso **idêntico** ao anterior: mesmo texto, mesma classe, mesmos 1800 ms) e vermelho, por 6 s, dizendo que não copiou e que o texto já está selecionado para `Cmd+C`. Textarea vazia também deixou de dizer "Copiado!". O temporizador passou a ser um por aviso, cancelado antes de reagendar: dois cliques seguidos no mesmo botão faziam o timer do primeiro esconder o aviso do segundo.
- **Âncora do calendário (aba Leads) — validar seletor, não escapar**: a mesma âncora tem dois destinos no bloco entregue (string JS `ANCORA` e **seletor CSS** da regra do plano B). Dentro de `<style>` o parser está em RAWTEXT: ignora `</` genérico e `<!--` e só reage a `</style`, então `escJs` ali é inerte — o campo continuava executando código arbitrário mesmo depois da correção de escape (`reserva</style><img src=x onerror=…>` executa e derrama o CSS como texto; `reserva{}*{display:none}#x` esconde a página inteira). O tratamento certo para destino CSS é **validar o seletor**: aceita-se `#` + letra + letras/números/hífen/sublinhado (`lAncOk`), e fora disso a geração é recusada com aviso. De quebra, isso barra o caso realista e igualmente mudo de âncora com espaço ou acento, que gerava seletor inválido e plano B que não funcionava.

- **Pergunta negativa é defeito de interface** (fase 4, ago/2026 — aba Contagem regressiva). O controle da coruja no celular perguntava "**Esconder no celular?**" com **Sim** marcado por padrão: quem ligava a coruja não a via no celular e concluía que o recurso estava quebrado. O controle funcionava; a pergunta é que obrigava a segurar duas negações ("sim, esconda") para prever o resultado, e o padrão contrariava a expectativa de quem acabou de ligar um enfeite. Agora a pergunta é positiva — "**Mostrar no celular?**", **Sim** por padrão — e a coruja aparece no celular por definição. **A chave gravada mudou de nome junto com o sentido** (`corujamob` → `corujamostrarmob`), e é essa a parte não negociável: manter o nome antigo com o valor invertido reinterpretaria em silêncio o que o operador já tinha configurado. `cRestaura` traduz o estado antigo uma vez (`corujamob: 'sim'` ⇒ `mostrar: 'não'`, e vice-versa), então quem já tinha escolhido continua com a escolha dele; o padrão novo só vale para quem nunca configurou. No gerador, `cfg.coruja.mob` virou `cfg.coruja.escondermob` — o nome antigo dizia só "celular" e ficava a um passo de ser lido como o contrário do que valia. A tradução testa por `'nao'`, não por `'sim'`: a versão anterior deixava qualquer valor inesperado (vazio, lixo) no padrão dela, que era **esconder**, e testar pelo outro lado faria estado corrompido cair em "mostrar" — assimetria não intencional. **A migração é de mão única**: no primeiro save a chave antiga some do estado, então reverter a publicação para a versão anterior devolveria todos os operadores ao padrão antigo (esconder) sem aviso. Aceitável — o estado é do navegador de uma pessoa e a re-expressão está visível no rótulo —, mas quem cogitar um rollback precisa saber disso. Precedente da mesma família no arquivo: `corujagap → gap`.
- **Piso e teto no mesmo número se anulam** (fase 5, ago/2026 — aba Contagem regressiva, R21 e R22). O liga/desliga da coruja virou **escolha de posição** (`nao` | `esq` | `dir` | `ambos`) e o campo de altura virou **teto**: a coruja acompanha a altura da barra e para nesse valor. O recurso é **só CSS** — `align-self:stretch` estica o quadro dela até a altura da linha do flex, o desenho vai posicionado de forma absoluta dentro do quadro e o quadro tem **largura fixa igual a `teto×32/38`** (a proporção do `viewBox`): com o `preserveAspectRatio` padrão, o SVG passa a caber pela largura assim que o quadro fica mais alto que o teto, e a altura renderizada para exatamente no teto. Nada de medir altura por JavaScript e reagir a `resize`. **A armadilha, registrada porque custou uma reimplementação:** a primeira versão punha também `min-height:teto` no quadro, para uma barra de uma linha continuar idêntica à de antes. Com isso a linha nunca ficava abaixo do teto, e `min(teto, linha)` dava **teto sempre** — a coruja voltava a ser tamanho fixo e o recurso nascia letra morta. Piso e teto no mesmo número se anulam; só há crescimento visível se o piso for menor que o teto. Como o dono decidiu que o número é o **teto** ("não uma escolha entre fixo e automático": o modo fixo saiu), o piso caiu. **Consequência registrada:** numa barra cuja linha é mais baixa que o teto (texto curto, sem botão de ação e sem botão de fechar) a coruja agora acompanha a linha em vez de esticar a barra até o teto; a condição é a linha ser mais baixa que o teto. Com o teto padrão de 26 px, barra com botão de ação não muda; a partir de ~30 px de teto, muda também nela — com teto 60 o desenho cai de 59,99 para 30,33 px. E como a largura do quadro é `teto×32/38`, subir o teto alarga o espaço reservado nas pontas mesmo quando a coruja não cresce, estreitando a coluna de texto e antecipando a quebra de linha. As corujas continuam **irmãs** de `.fcb-conteudo`, nunca filhas: só o miolo tem `overflow:hidden` e só ele abriga o trilho da rolagem. **Compatibilidade:** chave nova (`corujapos`), mesmo princípio do `corujamob → corujamostrarmob` — `cRestaura` traduz o estado antigo uma vez, e `'sim'` vira `'ambos'` (quem tinha a coruja ligada a tinha nas **duas** pontas; escolher um lado por ele seria reinterpretar em silêncio). O teste é por `'sim'`, e não por `'nao'`, para estado corrompido continuar caindo no padrão antigo, que era **não usar**. O teto entrou na tabela `C_NUMS`, que alimenta `fcPreso`/`fcAjustar`: o campo se corrige à vista no `change`/`blur` e na carga, porque teto zero ou negativo geraria quadro de largura zero — coruja ligada e invisível, defeito mudo.
- **Quatro recursos e uma prévia que deixou de imitar o gerador** (fase 5, ago/2026 — aba Slideshow, R4 a R7). Entraram: **proporção própria no celular** (`s-pm` + corte `s-mob`), **ordem aleatória** (`s-ordem`), **setas e bolinhas** com liga/desliga independentes (`s-setas`, `s-dots`) e **arrastar/pausar** (`s-arrastar`, `s-pausar`). Quatro pontos ficam registrados:
  - **A prévia passou a executar o bloco gerado**, no padrão que a Contagem regressiva firmou: `sCfg()` lê a interface, `sBloco(cfg)` monta o bloco, `sGerar` escreve o retorno na textarea e `sPvMontar` escreve o **mesmo** retorno num iframe de mesma origem por `document.write`, com shim de `localStorage`/`sessionStorage` em memória (conferido, com aviso visível se não pegar), enchimento cinzento abaixo, debounce de 400 ms com timer único e montagem só ao abrir a aba. A prévia antiga era uma segunda implementação completa (marcação `.pv-*`, motor próprio de troca de slide, CSS próprio) e já tinha divergido no limite do intervalo; ela não teria como mostrar ordem aleatória, arrastar nem pausar sem que os quatro recursos fossem escritos duas vezes. As regras `.pv`/`.pv-slide`/`.pv-seta`/`.pv-dots` saíram do `<style>` da ferramenta junto com ela. Medido: o texto do `<script>` e do `<style>` dentro do iframe é **idêntico** ao da textarea.
  - **A proporção do celular é um `@media` novo, depois da regra base, mexendo só em `aspect-ratio`** — não uma segunda regra `.fc-slideshow`. O `touch-action:pan-y` do arrastar, esse sim, foi **acumulado dentro da regra base**, porque uma segunda regra de mesma especificidade apagaria o `background` dela por inteiro. Mutação de conferência: emitir o `@media` **antes** da regra base faz a proporção do celular nunca valer (medido: 400 px de viewport continuou renderizando 3:2 em vez de 3:4), que é exatamente o defeito mais repetido desta série.
  - **O embaralhamento é Fisher-Yates sobre `IMAGENS`, uma vez por carregamento e antes de montar os slides** — é isso que faz a **primeira** foto variar também. Mutação de conferência: restringir o sorteio a `j ≥ 1` mantém dez ordens diferentes em dez carregamentos e ainda assim entrega sempre a mesma foto de abertura; meia solução que passa despercebida sem olhar a primeira posição.
  - **Setas e bolinhas desligadas juntas avisam, não recusam.** Nesta aba a passagem automática **não tem como ser desligada** — não existe campo para isso —, então a combinação não prende ninguém na primeira foto (medido: sem setas e sem bolinhas, com 1500 ms, o índice ativo andou 0→1→2→3 sozinho); ela apenas tira do visitante a escolha de qual foto ver, que é vitrine legítima. Recusar bloquearia um layout válido e nada está indefinido para o gerador ter de adivinhar; corrigir em silêncio (ligar uma seta por conta própria) seria a troca de defeito visível por invisível que o projeto já recusou. O aviso fica ao lado dos próprios campos e muda de texto conforme o arrastar esteja ligado ou não.
  - **Pausar tem três origens independentes, e não um booleano** (rodada de correção): `mouseenter`/`mouseleave`, `focusin`/`focusout` e `touchstart`/`touchend`+`touchcancel` guardam cada uma o seu estado (`pMouse`, `pFoco`, `pToque`), reavaliados a cada evento por uma `repensar()`; `agendar()` só volta a agendar com as três soltas. Com um booleano único, a primeira origem que soltasse zerava a pausa das outras: em aparelho híbrido o `touchend` religava o rodízio com o ponteiro ainda sobre a foto, e o `mouseleave` religava com o foco ainda numa seta — este último cancelando justamente a pausa de quem navega por teclado, que era o motivo de o `focusin` existir. **Estado por origem, e não contador**: contador se desequilibra quando um evento vem repetido ou falta (dois `touchstart` e um só `touchcancel`) e deixa a pausa presa para sempre, que é falha muda e permanente; estado por origem é idempotente.
  - **Arrastar não pode quebrar a rolagem vertical**: o eixo é decidido na primeira movimentação acima de 8 px e gesto mais vertical que horizontal nunca troca foto; nenhum `preventDefault` é chamado (os três ouvintes são `{passive:true}`) e quem impede rolagem horizontal é o `touch-action:pan-y`. Mutação de conferência: remover a decisão de eixo faz o gesto **diagonal** (−70 px na horizontal, −160 na vertical, que é rolagem de página) trocar de foto — o gesto puramente vertical sobrevive por acaso, por causa do limiar de 40 px de distância, que é uma segunda guarda mais fraca.
  - **Padrão de todos os quatro é "como era antes"**: setas e bolinhas ligadas, ordem cadastrada, sem proporção de celular, sem arrastar e sem pausar. Com tudo desligado o bloco sai **byte a byte** igual ao das versões anteriores (medido por SHA-256 contra a `main`, nas seis abas). `sRestaura` cai nesses mesmos padrões quando o estado gravado é de uma versão anterior: restaurar configuração antiga não pode ligar recurso nenhum.
- **Sete recursos no pop-up, e a promessa que o horário não pode furar** (fase 5, ago/2026 — aba Captação de leads, R8 a R14). Entraram: horário de atendimento, pergunta de qualificação, posição do botão flutuante, os cinco efeitos de destaque, movimento do conteúdo do cabeçalho, cores da coruja e posição da coruja. O que fica registrado:
  - **Fora do horário o pop-up avisa, mas não fecha a porta.** O botão continua abrindo, o formulário continua enviando e a mensagem continua indo para o WhatsApp — mensagem de WhatsApp fica esperando, então barrar o recado só perderia o lead sem proteger ninguém. O que muda é a **promessa**: um aviso aparece no topo do formulário. E ele é recalculado **em cada abertura do pop-up**, não uma vez na carga da página: uma aba deixada aberta atravessa a virada das 18h, e calcular na montagem faria o visitante ler "respondemos agora" às 18h05 (medido: mesma página, fechada às 17:59 e reaberta às 18:01, mostra o aviso na reabertura).
  - **O fuso é fixo no código gerado**, como na data-alvo da Contagem regressiva: `HORARIO_FUSO=-3` (Brasília, sem horário de verão desde 2019), e o instante é convertido antes de qualquer comparação. O relógio do visitante pode estar em qualquer lugar — viagem, aparelho desacertado, cliente de fora — e o horário de atendimento é o **do fotógrafo**, não o do visitante. Usar a hora local do aparelho faria o mesmo instante ser "dentro" para um e "fora" para outro. Medido com o fuso zerado por mutação: às 08:59 de Brasília o bloco passa a dizer que está aberto.
  - **A conversão leva DUAS passadas, e a razão não é obviedade** (rodada de correção 1). `getTimezoneOffset()` responde pelo instante em que é **lido**, mas a leitura de parede (`getDay`/`getHours`) acontece no instante **já deslocado**. Se os dois caírem em lados opostos de uma virada de **horário de verão do visitante**, o deslocamento sai uma hora errado. A segunda passada reaplica o deslocamento com o offset lido no instante deslocado, que é o offset que os getters vão de fato usar. Medido em `TZ=Pacific/Auckland`, varrendo 2026 minuto a minuto com atendimento nos sete dias: a versão de uma passada só diverge em **120 minutos do ano**, em duas janelas de uma hora (04/04 17:00–17:59 e 26/09 18:00–18:59, hora de Brasília) — na segunda ela diz "estamos abertos" com o expediente já encerrado. `Australia/Sydney` dá as mesmas duas janelas; `Europe/Lisbon` e `America/New_York` não divergem em 2026, porque o deslocamento menor mantém as duas leituras do mesmo lado da virada. Com atendimento **seg–sex** a divergência é zero: as janelas afetadas caem no fim de semana em Brasília — ou seja, o defeito ficava mascarado justamente na configuração mais comum, que é o pior jeito de um defeito existir.
  - **Faixa que cruza a meia-noite é aceita** (20:00 → 02:00): o dia marcado é o dia em que o expediente **começa**, e a madrugada do dia seguinte conta como sendo dele. **Abertura igual a fechamento é recusada** com aviso, porque não há leitura única — pode ser 24 horas ou zero minuto. **Sem dia marcado ou com horário em branco o modo fica desligado** e o bloco sai sem uma linha sequer do recurso (byte a byte igual ao de antes dele), mas o desligamento **aparece na tela**: um aviso âmbar ao lado dos campos diz que o modo está desligado e por quê.
  - **A resposta da pergunta de qualificação é opcional para o visitante.** Uma pergunta obrigatória custaria leads e o recado é o que importa. Escolhendo alguma coisa, a mensagem ganha uma linha entre a página e o código (`Interesse *Ensaio newborn*.`); sem escolher, a linha não existe e a mensagem sai **idêntica** à de quem não usa o recurso (medido: as duas strings são iguais). A lista é um `<select>` populado por `textContent` a partir de um array de strings — nada de opção montada por concatenação de HTML —, e o gate do recurso é a lista estar vazia, não um radio a mais.
  - **Uma regra CSS por seletor, sempre.** Brilho, degradê e tremor animam o mesmo `.fcw-topo` e são acumulados numa **única** regra: as camadas de `background-image`/`size`/`repeat` vêm depois do `background` shorthand dentro da mesma regra, e as três animações entram numa lista só (elas não disputam propriedade — duas animam `background-position` e uma anima `transform`). Pulsar fica em `.fcw-titulo` e não em `.fcw-topo` justamente para os dois `transform` não se atropelarem. Medido: com os cinco efeitos ligados, o CSS gerado tem exatamente **uma** regra `.fcw-topo` e **uma** `.fcw-titulo`.

O teste é por `'false'`, e não por `'true'`, para estado corrompido continuar caindo no padrão antigo, que aqui era **com** coruja (a versão anterior deixava valor desconhecido no padrão do HTML). As **cores** da coruja também vêm com portão explícito (`auto` | `livre`): "auto" emite exatamente a chamada de antes, `svgCoruja(COR_TOPO_POPUP)`, e só "livre" acrescenta a função `svgCorujaTopo()` com as duas cores.
  - **A prévia passou a executar o bloco gerado**, terceira aba a fazê-lo: `lCfg()` lê a interface, `lBloco(v)` monta o bloco, `lGerar` escreve o retorno na textarea e `lPvMontar` escreve o **mesmo** retorno num iframe de mesma origem. A prévia antiga era um desenho estático do pop-up com estilos inline próprios — não tinha botão flutuante, nem comportamento nenhum — e com sete recursos entrando divergiria em todos eles de uma vez. Além do shim de storage, este quadro neutraliza mais duas coisas **do ambiente, nunca do bloco**: `HTMLElement.prototype.focus` (o bloco foca o campo nome 100 ms depois do clique, e a prévia abre o pop-up sozinha a cada atualização — o cursor do operador seria roubado do formulário ao lado a cada 400 ms de digitação) e `window.open` (experimentar o botão enviar abriria o WhatsApp de verdade). As três trocas são conferidas depois e denunciadas num aviso vermelho visível se não pegarem, porque as três falhariam caladas. A abertura automática do pop-up é escrita **depois** do bloco, como o enchimento: sem ela o quadro mostraria só o botão, e seis dos sete recursos vivem dentro do pop-up.
  - **Acento em texto que o visitante lê: permitido, e a análise fica registrada** (rodada de correção 1, para não ser reaberta). O item 10 do manual do Prosite diz "sem acentos em código colado; **textos visíveis com acento OK**", e há precedente publicado: `MSG_FINAL='Promoção encerrada'`, da Contagem regressiva. O padrão `Escolha uma opção (opcional)` (opção vazia do `<select>`) e o aviso de horário são **texto visível**, escritos por `textContent`, então mantêm a acentuação correta. O que *parecia* uma convenção ASCII nesta aba não é: os sete textos do pop-up (`Fale com a Foto Certa`, `Seu nome`, `Como podemos te chamar?`, …) simplesmente **não têm nenhuma palavra que precise de acento** — a questão nunca tinha aparecido. O que é convenção deliberada são os quatro trechos da **mensagem do WhatsApp** (`Ola`, `meu nome e`, `voce`), com o acento removido de propósito; `PERGUNTA_MSG` ("Interesse") segue essa mesma linha por ir para o mesmo destino. Consequência prática desta análise: o aviso de horário, que na primeira entrega saía como "horario", foi corrigido para **"horário"** — ele é visível ao visitante, e sair sem acento era a inconsistência real.
  - **A lista da pergunta recusa duplicata e tem teto** (rodada de correção 1). Cadastrar duas vezes o mesmo texto produzia duas linhas indistinguíveis no `<select>`: o visitante escolhe uma das duas, a mensagem chega igual nos dois casos e o operador nunca fica sabendo. Recusa com aviso, nomeando a posição da opção já cadastrada, comparando sem maiúsculas nem espaços das pontas — e o texto digitado **fica no campo** para ser corrigido, em vez de sumir. O teto de 20 opções não é limite técnico: uma lista maior deixa de qualificar e vira rolagem dentro do pop-up, que no celular já é apertado.

Sem efeito visível, mas é resíduo que o próximo leitor tem de decifrar. O nó continua sendo criado (o ponto piscando entra **antes** dele, então o texto não pode mais ser filho direto do título); o que passou a ser condicional é só a classe.
  - **Padrão de todos os sete é "como era antes"**: coruja à esquerda com as cores de antes, cabeçalho estático e sem efeitos, botão à direita a 92 px do rodapé, horário desligado e nenhuma opção de qualificação cadastrada. Com tudo desligado o bloco sai **byte a byte** igual ao das versões anteriores (medido nas seis abas contra a `main`: 13 889 caracteres, mesmo hash).
- **Fase 5 — Agendamento TidyCal (dois recursos):** conferir o endereço antes de publicar, e alturas por situação em vez de por pixel.
  - **Botão que abre a página de teste (R15).** Dois botões, um por endereço: o do **caminho do booking type** abre `https://tidycal.com/` + o caminho digitado numa aba nova; o da **página intermediária** abre o endereço do campo, e só aparece no modo "página intermediária embutida". Os dois recusam com aviso em vez de abrir endereço torto. O caminho passa por `tPathOk`, que aceita apenas segmentos (`letras, números, . - _` e barra entre eles): sem esse limite, um `:` ou um `//` digitado no campo faria o prefixo virar parte de **outro** endereço (`..//evil.com/x` resolve para outro host), e o botão abriria uma página que não é a que o código vai embutir. A validação é **do botão, não do gerador**: `tGerar` continua exatamente como estava, porque o recurso é sobre conferir, não sobre passar a recusar caminhos que hoje geram código. O botão da intermediária recusa o **caminho relativo** (`/iframe-…`), que é válido no código 3 — lá ele é resolvido no domínio do site — mas aqui seria resolvido no domínio da ferramenta e abriria uma página inexistente; dizer por que vale mais do que abrir a página errada. `tPathNorm` é uma implementação só, usada pelo botão **e** por `tGerar`, senão o endereço conferido e o endereço embutido poderiam divergir.

O preset **não é um modo**: escolher um apenas **escreve os dois números nos campos**, que continuam editáveis — nada fica escondido atrás do rótulo. Mexer numa altura reconsulta a tabela e a marca volta para "ajuste fino" na hora (e volta sozinha ao preset se o operador digitar de novo o par exato), pelo mesmo motivo que derrubou o rótulo do halo na aba Bordas: rótulo que descreve outra coisa que não o campo é defeito, mesmo quando o campo está certo. A **largura de corte do celular não entra no preset** — ela descreve o tamanho da tela, não o tamanho do formulário, e 700 é validado independentemente do tipo de agendamento. Estado gravado por versão anterior não tem a chave `preset`: em vez de deixar o rádio no padrão do HTML (que diria "formulário padrão" sobre alturas que podem ser outras), a marca é **deduzida das alturas restauradas** (`tPresetInferir`), e a prensa da faixa na carga pode rebaixá-la para "ajuste fino".
- **Fase 5 — Bordas com efeito (três recursos):** conferir a cor no contexto certo, guardar identidade e juntar dois efeitos num bloco só.
  - **Prévia sobre fundo configurável (R18), e por que esta prévia *não* virou iframe.** Quatro opções — papel da ferramenta, página clara, página escura e cor livre —, aplicadas ao fundo da área de prévia. Serve à lição já registrada de que cor renderizada muda com o contexto: o halo é `rgba()` e se **mistura** com o que está atrás (medido: o mesmo halo compõe `rgb(255,236,192)` sobre branco e `rgb(102,83,39)` sobre `#141414` — distância RGB de 264), e o mesmo miolo `#8A4A32` sai de 6,76:1 de contraste contra uma página clara para 2,72:1 contra uma escura. A escolha é **só da prévia**: não passa por `bMontar`, não entra em `cfg` e os códigos 1 e 2 saem idênticos com qualquer fundo (verificado). A conversão para o padrão iframe das abas Slideshow, Leads e Contagem foi **avaliada e recusada**, e a razão precisa ficar registrada porque o padrão é regra do projeto: aquele padrão desfaz **duplicação de implementação**, e aqui não há duplicação — `bPreview` chama `bMontar`, a mesmíssima função de `bGerar`, e aplica no elemento exatamente a string do código 2, com exatamente o `@keyframes` do código 1 num `<style>`. Um iframe traria um shim de storage para proteger chaves que esta aba nunca escreve (o bloco entregue é CSS puro, sem uma linha de JavaScript) e um debounce para uma montagem que custa uma atribuição de `cssText`. O que continua diferindo da página publicada está escrito na legenda do quadro: tipografia e vizinhança são as da página real.
  - **Biblioteca de presets (R19).** Salvar a configuração da aba sob um nome, listar, aplicar e remover. Mora **dentro do fragmento `b`** do estado (`b.presets`), e não numa chave de topo nova: a lista `ABAS` e a estrutura de isolamento por aba ficam intocadas, e a biblioteca é preservada pelo mesmo `fcFrag` que preserva o resto da aba. `bCampos()` é a leitura única do que a aba grava **e** do que um preset guarda, e `bAplicarCampos()` a escrita única de ambos — com duas cópias, um campo novo entraria no estado e não no preset, e o preset voltaria pela metade sem nada avisar. O preset guarda também o **fundo da prévia**, que é como aquele efeito se confere; não guarda a biblioteca nem a escolha de consolidação, que é sobre outro componente. **Nome repetido substitui, depois de confirmar** — comparação sem diferença de caixa e sem espaço nas pontas —, porque a lista e a consolidação identificam o preset **pelo nome**, e dois iguais deixariam de dizer qual é qual. `fcAjustarTodos` roda **antes** de congelar os números, para um preset não devolver, meses depois, um valor que o próprio campo já não aceita. Limite honesto, escrito na ajuda: presets vivem no `localStorage` **deste navegador** — não acompanham outro computador e somem se os dados do site forem limpos; o que viaja é o código gerado. Biblioteca gravada torta vira lista vazia em vez de derrubar a aba, e o teste é por Array de verdade (`Object.prototype.toString`): um **texto** gravado no lugar da lista também tem `.length` e passaria por *duck typing*, desenhando um item por caractere.
  - **Código 1 consolidado (R20).** Uma caixa de seleção lista os presets salvos de efeito animado; escolhido um, o código 1 sai com as **duas** animações e as **duas** regras de movimento reduzido, num `<style>` só, em vez de dois blocos concorrentes colados no mesmo campo. Os parâmetros do segundo efeito vêm **do preset, não da tela** — as listras dependem da espessura da listra e o pulso do alcance, da intensidade e da cor; gerar o segundo bloco com os números do componente que está na tela produziria uma animação que não é a daquele outro componente (verificado: com 10 px salvos e 40 px na tela, o bloco consolidado mantém os 28,28 px do preset). Isso exigiu `bMontar` passar a **receber a configuração** em vez de ler o DOM por dentro — `bCfgDom` e `bCfgPreset` alimentam o mesmo gerador, no desenho do `cBloco(cfg)` da Contagem regressiva. `bPresoDe` espelha `fcPreso` para valores que não têm campo na tela, lendo a **mesma** linha de `B_NUMS`. **A limitação conhecida não é resolvida nem piorada:** efeitos diferentes têm nomes de animação diferentes e convivem; o mesmo efeito com parâmetros diferentes colide, e por isso consolidar um preset do **mesmo** efeito da tela é **recusado com aviso** — emitir dois `@keyframes fc-borda-listras` deixaria a página escolher em silêncio (medido na mutação: sem a recusa, saem dois blocos de mesmo nome). Na borda fixa a caixa some, porque não existe código 1. O nome do preset **não** entra no comentário do CSS: é texto livre do operador, e a sequência que fecha comentário CSS digitada ali fecharia o comentário mais cedo; o que identifica o bloco é o nome do efeito, que sai de uma lista fechada.
- **Fase 5 — rodada de correção 1 (TidyCal e Bordas).** Três pontos que a revisão pegou depois da entrega:
  - **A prévia das Bordas não obedecia "reduzir movimento".** `bPreview` injetava só o `@keyframes` (`m.keys`) e deixava de fora o `@media (prefers-reduced-motion: reduce)` do código 1: num aparelho com a preferência ligada, o operador via a borda girando na prévia e a borda parada na página publicada — a prévia mentia justamente para quem a regra de acessibilidade atende. Agora o `<style>` da prévia leva as duas partes, e o cabeçalho da regra virou a constante `B_MEDIA_RM`, usada pelo código 1 **e** pela prévia (duas cópias da mesma condição poderiam passar a casar coisas diferentes sem ninguém notar). Medido com o navegador emulando a preferência: os quadros resolvidos viram `["0px, 0% / 0px, 0%", "0px, 0% / 0px, 0%"]` e a posição do fundo não muda entre duas leituras a 350 ms — o mesmo quadro que o código entrega; na versão anterior, ela andava de 2,92% para 12,10%.
  - **A guarda da biblioteca de presets era rasa.** Testar só `Object.prototype.toString.call(x)==='[object Array]'` cobria dois dos quatro casos: `["texto"]` renderizava `undefined — borda undefinedpx`, e `[null]` estourava `TypeError` e jogava a aba em só-leitura (a rede da fase 2 segurava — falha visível, outras abas intactas —, mas a aba parava por causa de um item podre). `bPresetsLer` passou a filtrar **item a item** (`bPresetValido`: `nome` texto não-vazio, `cfg` objeto com `efeito` texto), e o que fica de fora é **anunciado** num aviso vermelho dentro da aba, com a contagem — dado corrompido não some calado.
  - **O clamp da faixa tinha duas cópias.** `bPresoDe` (fase 5) repetia as sete linhas de `fcPreso` mudando só a origem do valor: a faixa tinha fonte única, o algoritmo não. `fcPrender(faixa, valor)` foi extraído — `fcPreso(tabela,id)` mantém assinatura e comportamento e passou a chamá-lo, e `bPresoDe` virou uma linha. Provado com 41 valores de fronteira em seis campos de três abas (mínimo, máximo, fora dos dois, vírgula decimal, texto e vazio): saída idêntica à da versão anterior. **Consequência para quem for mexer:** o clamp agora se muda em um lugar só, e a regra "a tela e o código não podem divergir" passou a valer também para valores que não têm campo na tela.
  - Três acertos menores junto: a legenda do código 1 dizia "dois efeitos na mesma página" quando o destino é o cabeçalho do **site**; o aviso do endereço da intermediária descrevia campo vazio mesmo quando o campo estava preenchido e torto (agora são dois avisos, e o segundo cita o valor digitado); e `tPathOk` passou a recusar `.` e `..` como **segmento** de caminho — o host nunca saía de tidycal.com, mas o botão existe para o operador conferir o endereço que vai ser embutido, e `fotocerta/../outro` não é o que ele leu no campo (ponto dentro do nome continua valendo).
- **Link de imagem também é campo que precisa recusar** (fase 4 — aba Slideshow): `sAdd` só checava se o campo estava vazio, então "foto do natal", o nome de um arquivo do computador ou um caminho colado do Finder entravam na lista, saíam no `src` do código gerado e a foto simplesmente não aparecia — defeito descoberto **depois** de publicar. `sUrlOk` segue a mesma **postura** de `cUrlOk` (Contagem) e `tUrlOk` (TidyCal) — validar o formato e recusar com aviso, sem reescrever —, mas **o critério é deliberadamente diferente do `tUrlOk`**, e a diferença precisa ficar registrada assim, e não como paridade: aceita `http(s)://host…`, **aceita `//host…`** (que o `tUrlOk` recusa, porque lá o destino é uma página do próprio site e `//host` sairia da origem sem o operador perceber — aqui o caso normal já é outro host, o storage da Alboom) e aceita **caminho a partir da raiz** `/fotos/foto.jpg`, que é o único dos três que fica na origem: chamar esse terceiro formato de "caminho do próprio site" descreveria mal o conjunto. Recusa o resto, inclusive `javascript:`, `data:` e **barra a mais ou barra invertida no começo**: `///foto.jpg` resolve para `https://foto.jpg/`, `/\evil.com/x` resolve para outro host e `//` sozinho volta para a própria página — os três são erro de digitação de quem quis `//` ou `/`, saem da origem em silêncio e produzem exatamente a foto que nunca carrega. (A primeira versão da `sUrlOk` aceitava os três, por terminar em `charAt(0)==='/'`; o teste passou a exigir uma barra só e nenhuma barra invertida depois dela, como o `tUrlOk` já fazia no caso dele.) A conferência roda **duas vezes** de propósito — no cadastro e de novo em `sGerar`, percorrendo a lista e dizendo a posição —, porque a lista também chega pelo `localStorage`, gravada por uma versão que aceitava qualquer texto: sem a segunda passagem, quem já tem link torto salvo continuaria gerando código com foto que nunca carrega.
- **Agrupamento por assunto, e campo irrelevante não fica na tela** (fase 4, arrumação sem mudança de saída): na **Leads**, a seção 4 juntava a paleta do pop-up com a âncora do calendário, dois assuntos sem relação — a paleta desceu para a seção 3 (que virou "Mensagem, textos e cores do pop-up") e a âncora ficou com seção própria, com o passo a passo do Prosite promovido a fieldset da coluna direita para equilibrar a altura (e some junto quando a âncora não é incluída). Ainda na Leads, o campo **Emoji antes do título** só vale com a marca em "Emoji / nada": com a coruja SVG marcada — que é o padrão — ele ficava na tela sugerindo que fazia algo, e o que fosse digitado ali era descartado sem aviso; passou a aparecer só quando vale (`lEmojiToggle`, mesmo mecanismo do `l-anc-campos`). No **Checkout**, o "Código do pedido" saiu do fieldset "Como o cliente vai pagar" — ele não configura forma de pagamento nenhuma, serve às três pontas (PayPal, txid do Pix e WhatsApp) — e ganhou fieldset próprio, "Identificação do pedido"; e o botão "Gerar código", que estava aninhado na coluna direita, foi para a `div.acoes` em largura total logo abaixo do cabeçalho da última seção, como manda o padrão e como as outras abas já faziam.

- **Checkout, fase 5 — sinal, quantidade e resumo copiável** (ago/2026). A aba que mexe em dinheiro ganhou três recursos, e a ordem de cálculo é fixa e não negociável: **quantidade multiplica → cupom incide sobre o total → o sinal sai do total já com cupom → o desconto Pix não se aplica sobre o sinal**. O que ficou decidido, além do que o spec já mandava:
  - **A prévia foi convertida para executar o bloco gerado.** Ela redesenhava o carrinho com código próprio e já tinha divergido uma vez (mostrava o primeiro produto marcado e um total enquanto o carrinho publicado abria zerado). Com sinal, quantidade e resumo entrando, seriam três lugares novos onde a divergência pode nascer — a duplicação foi removida em vez de multiplicada. Hoje há `uCfg()` (uma leitura da interface) e `uBloco(cfg)` (uma montagem), e a prévia escreve o retorno de `uBloco` num `<iframe>` de mesma origem, como Contagem, Slideshow e Leads. **Duas trocas do ambiente da prévia, com o bloco entregue intacto**: storage em memória (com conferência e aviso vermelho se a troca não pegar) e o **SDK do PayPal substituído pelo desenho** que a prévia antiga já usava — carregá-lo de verdade mandaria o Client ID do operador para fora a cada remontagem e, com o campo ainda vazio, mostraria no carrinho uma mensagem de erro de pagamento **falsa**. O script do QR Code continua sendo baixado, então o QR da prévia é o QR real do payload real.
  - **O desconto Pix e o sinal não convivem, e isso é visível.** O spec proíbe aplicar o desconto Pix sobre o sinal (seria desconto dobrado, já que o sinal sai de um total que pode ter cupom) e não diz o que fazer com o desconto no resto. Decisão: com sinal ligado, `DESCONTO_PIX` **não é emitido** — zerado na origem (`uCfg`), pelo mesmo mecanismo que já o zerava quando a forma de pagamento não é "os dois". O que **não** se fez foi esconder o campo: ele fica na tela, **desabilitado, com aviso âmbar** dizendo por que não vale. Esconder faria os 10% já configurados sumirem sem explicação — trocar defeito visível por invisível é o que este projeto recusa desde o `c-mob`. A alternativa descartada era aplicar o desconto ao **saldo**: seria inventar regra que o spec não autoriza, e prometer agora um abatimento sobre um pagamento que acontece depois, fora do carrinho.
  - **Duas recusas, em dois momentos diferentes.** Sinal fixo **acima do maior pedido que o carrinho consegue montar** (já contando o teto da quantidade) é recusado **na geração**: nenhum pedido seria pagável, e não há valor certo a assumir. Sinal maior que o total **do pedido em curso** é recusado **no carrinho**, com linha vermelha, `actions.reject()` no PayPal e Pix sem payload — recusar, não aparar, porque aparar cobraria um valor que o operador não configurou. Sinal fixo acima do pedido *mínimo* de propósito **não** é recusado na geração: pode ser piso de venda intencional, e quem avisa nesse caso é o carrinho, na hora. Com o pedido em zero quem avisa continua sendo a guarda de total zero que já existia — dois avisos simultâneos esconderiam um ao outro.
  - **Quantidade zero tem um corte só.** `produtoAtivo(i)` devolve falso quando a quantidade é zero, e é por ele que o item sai da conta, da descrição do PayPal, da mensagem do WhatsApp e do resumo. Com quatro cortes independentes, eles teriam como discordar. As quantidades do produto e do opcional são **independentes** (dois ensaios com um álbum somam dois ensaios e um álbum) — está escrito na ajuda do campo, porque é a leitura que o operador precisa confirmar.
  - **Com o resumo ligado, a lista de itens da mensagem do WhatsApp passa a vir do mesmo enumerador do resumo** (`itensEscolhidos`). Dois laços separados poderiam divergir na regra da quantidade zero e as duas listas discordariam caladas.
  - **O resumo nasce desligado** e a cobrança de sinal também, porque a regressão exige que o bloco com os recursos desligados saia **byte a byte** igual ao anterior. Cada recurso é emitido só quando ligado — nem CSS, nem variável, nem seletor a mais —, no mesmo padrão que a aba Leads firmou na fase 5.
  - **`U_NUMS` nasceu com três linhas** (`u-qtdmax`, `u-sinalpct`, `u-sinalfixo`). Os dois campos numéricos antigos da aba — largura e desconto Pix — **não** entraram: o clamp deles é outro (largura abaixo de 240 vira 420, não 240), e movê-los mudaria número cobrado sem que nenhum recurso desta fase pedisse.
  - **Conferência**: 21 combinações de quantidade × cupom × sinal nos três modos de pagamento, servindo por `localhost`, com o valor do PayPal lido do `createOrder` do próprio bloco e o valor do Pix lido do **TLV 54 do payload gerado** (e o CRC16 conferido a cada vez), mais 26 casos de borda e **quatro mutações na aritmética** — inclusive uma que aplica o desconto Pix sobre o sinal —, todas derrubando a conferência correspondente.
  - **A prévia tem de provar o código, não parecer com ele** (rodada de correção 1). Três defeitos da mesma família, e a regra que sai deles: *prévia que executa o gerador precisa executar também as recusas do gerador, e precisa dizer o que ela não executa*.
    - **As guardas eram só do gerador.** `uPvMontar` chamava `uCfg()` direto, então a prévia rodava configuração que o botão "Gerar código" se recusava a produzir — medido com a chave Pix `pix@fc com.br`: a geração era recusada e a prévia desenhava payload com **CRC válido e QR na tela**. As guardas saíram de `uGerar` para **`uRecusa(cfg)`**, função **pura** (não mexe no DOM: a correção à vista da chave e das faixas continua sendo de `uGerar`, que é o gesto deliberado do operador — a prévia roda a cada tecla e não pode reescrever campo nenhum). **O que a prévia mostra quando a configuração é recusada: o quadro da recusa, com o motivo.** A alternativa — último bloco válido rotulado como desatualizado — foi descartada: um bloco velho com etiqueta continuaria desenhando números que o operador lê antes de ler a etiqueta.
    - **O shim do PayPal virou sonda.** Ele guarda a configuração que o bloco passa para `paypal.Buttons` e, a cada mudança do carrinho, chama o **`onClick` e o `createOrder` do próprio bloco**, mostrando abaixo do desenho o valor que iria na ordem e a decisão do clique (segue ou recusa, com o motivo). Assim o valor do sinal e as recusas do lado PayPal ficam verificáveis **sem baixar o SDK e sem mandar o Client ID para fora**. A sonda **restaura** o `.fcu-msg` que o `onClick` tiver escrito — sonda que deixa rastro mostraria mensagem de recusa velha depois de o pedido voltar a ser válido. O que continua fora do alcance da prévia (e está escrito na legenda): o que depende da resposta do PayPal — janela de pagamento, captura e as mensagens de sucesso e erro que vêm dela.
    - **Editar cupom na lista não redesenhava.** Só o *código* do cupom chamava `uPreview`; valor, tipo e validade chamavam apenas `salvarEstado`. Com a prévia antiga (que nem aplicava cupom) o defeito era latente; com a prévia viva ele virou número errado à vista — cupom trocado de 10% para R$ 50 fixos e a prévia seguia mostrando o desconto velho. Os três passaram a redesenhar. **A textarea continua só se atualizando no clique de "Gerar código"**, como em todas as abas: gerar é ato explícito.
  - **Uma recusa só para o sinal.** `sinalRecusa()` devolve o **motivo**, e a linha vermelha do carrinho, o clique do PayPal, o botão do Pix e o resumo copiável leem dela. Antes eram testes separados, e um discordou dos outros: o **resumo imprimia "Total 250 / Sinal 700 / Restante 0"** enquanto as duas pontas de pagamento recusavam corretamente — o único elemento visível que não respeitava a recusa. Junto entrou a guarda que faltava, **sinal que arredonda para zero** (produto de R$ 0,40 com sinal de 1% mandava `"0.00"` ao PayPal e um TLV 54 `0.00` com CRC válido): é o espelho da guarda de total zero que o pedido inteiro já tinha.
  - **Padrões de texto da aba são escritos sem acento** — `u-t6` já saía como "Nao foi possivel concluir o pagamento". `u-t10` nasceu com acento e foi alinhado; o rótulo do campo passou a dizer que o operador **pode** usar acento se quiser (o campo aceita, e `escJs` cuida do resto). São textos visíveis ao cliente, não código: a regra do manual não obriga, mas a aba inteira ficaria inconsistente com um padrão acentuado e nove sem.

- **Rodada de coerência da revisão final (ago/2026).** A revisão não achou defeito crítico; achou seis lugares onde a ferramenta tinha firmado um padrão e uma aba tinha ficado fora dele. As decisões:
  - **Faixa numérica: cobertura fechada nas seis abas.** Além dos catorze campos da Contagem (acima), entraram `u-descpix` e `u-largura` em `U_NUMS` e `l-resp` em `L_NUMS`. Os três clampavam **em silêncio**: 95 no desconto virava 90 e −10 virava 0 com o campo ainda mostrando 95 e −10; 200 na largura virava 420, que não é nem o valor nem o piso; −5 no respiro virava 24 e 999999 passava inteiro. Agora corrigem à vista, no `change`/`blur` e na carga. Estado gravado por versão anterior é corrigido **no campo** e regravado — medido: `c-alt=999 → 30`, `c-largmax=0 → 320`, `u-largura=200 → 240`, `l-resp=999999 → 400`, e o `localStorage` regravado com os valores corrigidos.
  - **`cUrlOk` alinhado ao `tUrlOk` — e a classe fechada nos dois.** A versão anterior terminava em `return true` e recusava só o que tivesse **esquema**: `//evil.exemplo.com/x` passava sem aviso e saía no `href` do botão de ação, enquanto o próprio alerta prometia âncora, caminho do site ou `http(s)` e a aba TidyCal já barrava exatamente esse caso. Passa a exigir **uma** barra no caminho do site. Consequência: caminho sem barra inicial (`natal-2026`) também passa a ser recusado — o alerta nunca o ofereceu, e ele muda de destino conforme a pasta onde o bloco for colado. **Emenda da re-revisão:** alinhar as duas abas fechou a coerência entre elas, não a classe do defeito — `/\evil.com/x` passava pelos **dois** validadores, porque o segundo caractere não era `/`, e o navegador resolve esse endereço como `http://evil.com/x` (medido). A limpeza que cada uma fazia por conta própria virou a função compartilhada `urlLimpa`, que faz o que o navegador faz antes de resolver a URL: tira controle e espaço **e normaliza barra invertida**. A limpeza vale só para o teste — o que sai no código continua sendo o que o operador digitou.
  - **"Alternar deslizando" + "pulsar": o efeito perde, e isso é visível.** Os dois animam o `transform` do **mesmo** `.fcb-conteudo`, e animação em execução vence transição na cascata: medido, durante a troca de mensagem o transform era `matrix(1.0037, 0, 0, 1.0037, 0, 0)` — escala pura, deslocamento vertical zero. O operador escolhia deslizar e via fade, sem erro nenhum. A escolha foi **não** duplicar elemento (a solução do Leads, que separou pulsar e tremor em `.fcw-titulo` e `.fcw-topo`, aqui exigiria um invólucro dentro de `.fcb-conteudo` que o `innerHTML` da troca de mensagem destrói, mexendo no motor mais delicado do gerador). Vale o padrão do **desconto Pix × sinal**: o campo fica na tela, **desabilitado, com aviso âmbar**, e o efeito é zerado na origem (`cCfg`). Vale para o pulsar contínuo **e** para o pulsar de urgência, que tem o mesmo conflito num seletor mais específico. Depois: `matrix(1, 0, 0, 1, 0, −11.36)` — translação pura, nenhuma escala.
  - **Tag Body é um campo compartilhado, e as instruções passam a dizer isso.** A aba Leads mandava "substitua todo o conteúdo do campo — não cole por cima"; a Contagem dizia "substituindo ou somando ao que já estiver lá". Seguir a primeira apagava a barra de contagem sem aviso. A orientação correta é a **convivência**: substitui-se o bloco anterior **do mesmo construtor**, e o que for de outro fica. Para a instrução ser executável, o bloco do Leads ganhou o cabeçalho de identificação que o da Contagem já tinha (`FOTO CERTA - BOTAO FLUTUANTE ...`), e o da Contagem ganhou duas linhas dizendo o que substituir — sem cabeçalho não havia como dizer "substitua **esse** bloco". A instrução traz também a **frase de transição** para quem já colou: bloco publicado antes desta rodada não tem cabeçalho, então "substitua o bloco deste construtor" não seria executável para ele — nesse caso o bloco antigo é o trecho do WhatsApp inteiro, do `<style>` das regras `.fcw-` até o último `</script>` desse trecho. Sem essa frase, quem não achasse "esse bloco" acabaria somando, que é justamente a duplicação que a instrução quer evitar.
  - **A âncora do Leads deixou de ter alcance global.** O bloco emitia `html { scroll-behavior: smooth }`, que suaviza **toda** âncora do site, inclusive as do tema Alboom, e não tinha guarda de movimento reduzido — exatamente o alcance que o bloco de Bordas foi reescrito para não ter. A regra saiu; a suavidade passou a ser do `window.scrollTo` do próprio script, que agora também atende o **plano B** (rola até a própria âncora quando o calendário ainda não carregou) e consulta `prefers-reduced-motion` **no clique**, devolvendo `'auto'` para quem pediu menos movimento. O `scroll-margin-top` da âncora fica: é folga, não movimento.
  - **Guarda de movimento reduzido nas seis abas.** TidyCal era a única sem: emitia `transition: min-height` e nenhum `@media`. Ganhou a regra que desliga a própria transição, e nada mais. Na Contagem, `cfg.urg.ativo` entrou em `temTransMov`: com urgência ligada e pulsar de urgência desligado, `anim` ficava vazio e o bloco inteiro deixava de sair, apesar de o CSS trazer `transition:background-color`. No Slideshow, o desligamento do zoom passou a sair **sempre**, porque a regra que **liga** o zoom já saía sempre: com duas galerias na mesma página, o bloco da galeria sem zoom vinha depois no documento, reemitia a regra e devolvia a animação a quem pediu menos movimento. Regra geral: **linha condicional não fecha regra incondicional**.
  - **Faixa de z-index declarada.** Os blocos reservam 99980 (barra de contagem, campo `c-z`), 99990 (botão flutuante) e 99991 (pop-up de captação). Nada dizia isso, e a ajuda do `c-z` convidava a subir. Medido com `c-z=99998`: no topo da tela o elemento clicável passa a ser o `.fcb-interno` da barra, por cima do overlay — o pop-up deixa de ser modal. O comportamento **não** foi travado (uma página sem o bloco de leads pode legitimamente usar valores altos); a faixa passou a ser declarada na ajuda do campo e num comentário no `lCss`, onde os dois maiores números são cravados.
  - **Duplicação que concorda hoje é dívida, não defeito** (fechada em ago/2026, na rodada seguinte). A revisão tinha registrado três trechos escritos duas ou cinco vezes que produziam saída idêntica. Unificar código correto não conserta nada hoje; o que se compra é que a próxima edição não possa mudar um lado só. A regra que saiu daí: **unifica-se a fonte que escreve, nunca a saída** — o bloco colado no site continua carregando a própria cópia, porque ele tem de funcionar sem a ferramenta. Detalhes dos três casos (cores, coruja, preço) e a prova de que a saída não mudou estão em §6.
  - **Código morto removido**: `uNum` (nunca chamada) e `L_PV_CORTE` (declarada com comentário e nunca lida, ao lado de dois números cravados). Constante que ninguém lê não documenta nada, só parece documentar: o 480 virou comentário em `lPvLargura`, que é onde ele de fato era consultado.

- Publicado e testado: hospedeira (leads + âncora + plano B), intermediária (TidyCal), a ferramenta de construtores, checkouts PayPal e Pix validados com pagamentos reais, e as bordas animadas nos blocos da landing de Natal.
- Pendente de teste na página publicada (gerado e validado tecnicamente em ago/2026): a aba **Bordas com efeito**, a aba **Checkout** na versão com seletor de formas de pagamento e múltiplos produtos — e, da fase 5, **cobrança de sinal, quantidade por item e resumo copiável**, cuja aritmética foi conferida no navegador mas ainda não passou por um pagamento real de sinal (PayPal e Pix) —, e a aba **Contagem regressiva**.
- **Fluxo de atualização**: editar o arquivo correspondente no repositório → commit + push. O GitHub Pages republica `construtores.fotocerta.com.br` sozinho, sem o antigo passo de colar o miolo em componente do Prosite. Os arquivos em `prosite/` continuam sendo colados à mão no painel da Alboom, pois são o espelho do que vive lá.
- **Pendência de teste — movimento reduzido no Safari**: a correção de acessibilidade das Bordas se apoia em redefinir o `@keyframes` dentro do `@media (prefers-reduced-motion: reduce)`, e foi medida em Chromium. É comportamento especificado (a última declaração daquele nome vence quando a media casa) e o WebKit moderno implementa, mas o projeto valida em Safari e o público da landing é majoritariamente Safari móvel. Confirmar na página publicada, em **aba anônima no iPhone com "Reduzir movimento" ligado**, que a borda **congela num estado visível** — nem continua animando (redefinição ignorada), nem some (que era o defeito antigo).
- **Pendência conhecida da landing de Natal**: `prosite/natal-2026/bordas-css-componentes.md` (espelho do que está publicado) ainda traz a regra antiga `[style], * { animation-duration: 0.01ms !important; … }` no bloco do head do site. Ela continua matando toda animação do site para quem tem movimento reduzido. Para trocá-la, regerar o código 1 na aba Bordas com o efeito usado no bloco, colar no lugar do bloco antigo e atualizar o espelho.
- **Decidido (ago/2026) — o teto de `c-horas` é 8760.** A contradição registrada aqui (`value="48"` contra `max="23"`) foi resolvida pelo dono a favor do padrão: **o `max="23"` é que estava errado**. Os três campos de duração se **somam** — `duracaoMs = ((dias*24+horas)*60+mins)*60000` —, então "horas" significa horas *adicionais*, não hora dentro de um dia, e não há motivo para parar em 23. O teto passou a ser **8760** (um ano em horas): preserva a liberdade real de quem prefere contar em horas e barra só o número absurdo, do tipo que nasce de um zero a mais. O número está nos **dois lados** — na linha de `c-horas` em `C_NUMS` e no atributo `max` do `input` — porque nenhum dos dois basta sozinho: o `max` não impede valor digitado, e a tabela sozinha deixaria a seta do teclado passar do teto. Nada encurta em silêncio: estado salvo acima de 8760 é corrigido **no próprio campo**, na carga e no `change`/`blur`, pela mecânica de `fcPreso`/`fcAjustar` que a aba já usa. Medido: campo em 48 e uma seta para baixo → 47 (era esse o risco do `max="23"`, que levava direto a 23); 99999 digitado → 8760 à vista no blur; −5 → 0; `localStorage` gravado com 99999 → campo em 8760 depois de recarregar. O rótulo do campo passou a declarar a faixa e a dizer que as horas se somam aos dias, para o próximo leitor não refazer a mesma pergunta.
- **Resolvido (ago/2026) — as duplicações que concordavam.** Os três trechos repetidos que a revisão final tinha deixado registrados foram unificados. Nenhum era defeito: os pares produziam resultado idêntico, e a saída dos seis geradores continuou **byte a byte igual** depois da unificação (26 saídas comparadas por SHA-256 entre as duas versões servidas em portas separadas de `localhost`, com `localStorage` limpo e página recarregada antes de cada roteiro). O motivo de mexer é a classe, não o sintoma: duplicação que concorda hoje diverge no dia em que um lado for alterado e o outro não — sem erro, sem aviso, exatamente como já aconteceu na prévia que imitava o gerador. O que foi feito:
  - **Rede de segurança das cores.** `corSegura` (compartilhada), `bCor` (Bordas) e `cCor` (Contagem) tinham corpo idêntico. Ficou só `corSegura`, o nome mais descritivo; as 16 chamadas apontam para ela, e o comentário que dizia "bCor e cCor … não são tocadas" foi corrigido.
  - **Desenho da coruja.** Eram cinco cópias das mesmas sete formas: o logotipo da ferramenta, a prévia do botão da aba Leads, as duas variantes que o bloco de Leads escreve (cor automática e cores livres) e a que o bloco da Contagem escreve. Agora todas derivam de `CORUJA_PECAS`, uma lista de formas com dois pontos variáveis (`{C}` corpo, `{D}` detalhes), no bloco de utilidades compartilhadas. Duas saídas: `corujaSvg(corpo,det)` devolve o desenho pronto para uso **aqui dentro**, e `corujaJs(ind,ind2,corpo,det)` escreve o `return` que vai **dentro do bloco entregue** — os parâmetros de indentação e de expressão de cor são a única coisa em que as três variantes geradas diferiam. O logotipo do topo deixou de ser SVG colado no corpo da página: virou um `<span>` vazio substituído na partida, em `prep('Logotipo do topo')` próprio, para uma falha ali não levar junto a barra de abas.
  - **Formatação de preço.** `uFmt` (o que a ferramenta mostra) e a `moedaFmt` que ela escreve dentro do carrinho passaram a sair da mesma tabela `PRECO_MOEDAS`. O real fica fora da tabela de propósito: é o padrão e é o único com vírgula decimal. A grafia `\u20AC` do bloco gerado é **derivada** do próprio símbolo por `precoJsTexto` — guardá-la como segunda coluna seria criar outra vez duas grafias para divergir.

  **A restrição que governa as duas últimas:** o bloco que o operador cola no site é **autossuficiente** e não pode depender desta ferramenta. As cópias que vão *para dentro* do código gerado continuam existindo lá — o que se unificou foi a **fonte que escreve essas cópias**, nunca a saída. Fazer o bloco gerado chamar algo de fora seria parar no lugar errado.
- **Migração do estado da ferramenta**: o `localStorage` é por origem, então o que estava salvo em `fotocerta.com.br/utl-construtor` não acompanha a mudança para `construtores.fotocerta.com.br`. Produtos, cupons e imagens cadastrados precisam ser recadastrados no novo endereço.
